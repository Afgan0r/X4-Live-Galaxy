## Required discovered-faction matrix

Every ID returned by `GetAllFactions(false)` must occur exactly once in the run
matrix as `included`, `excluded`, or `unknown`. Inventory absence does not erase
a discovered ID. `unknown` blocks Gate B closure.

The required included set covers ordinary, small, pirate, XEN, and KHK factions.
`player` is explicitly excluded. Service or temporary exclusions retain exact
first-party evidence and an inference label. A faction with zero ships remains
included with a partial zero-record core observation; it is not declared
authoritatively empty and does not produce detail sections.

## Required field matrix

For each included nonempty faction, retain at least two current-history cycles
for:

- core identity, owner, macro/type, class, location, and consistency reason;
- cargo ware item amounts and storage transport, capacity, and occupied volume;
- aggregate crew capacity, roles, counts, hireability, and raw tier thresholds;
- physical and virtual installed slots, both upgrade-group strings, software,
  missiles, and every returned unit category.

Each detail section must bind the exact faction-scoped core revision, member
revision, producer incarnation, transport epoch, and discovery policy context.
An ownership, location, type, or class change marks only the affected record
stale. It does not cancel unrelated factions or the full batch.

## Ordered runtime windows

1. Verify and install the reviewed package while X4 is closed.
2. Start X4 once, load the disposable campaign, leave normal game time running,
   and tell the agent when ready. Keep X4 running across the following windows;
   no restart is needed between normal, SETA, control, or bridge-recovery windows.
3. The agent starts `tools/run-heavy-ship-runtime.ps1` with
   `-Gate B -Mode Normal` and the current X4 PID, debug log, frame-capture
   binary, packaged bridge, approved limits, and private evidence root. The
   runner owns its bridge and capture processes, reports `capturing` in
   `runner-status.json`,
   then stops them and writes `runner-result.json`. The owner leaves normal
   game time running during the finite active window.
4. The agent records a same-session bridge-free FPS control window with the
   same foreground state, then performs finite bridge absence/reconnect and
   bridge-process restart checks. These are separate agent-orchestrated checks;
   the active-window runner alone does not certify them. The owner leaves X4
   running and need not change the game for these checks.
5. Only after the agent prompts, the owner enables approximately 6.2x SETA and
   confirms it is active. The agent starts the same runner with
   `-Gate B -Mode Seta`; it independently observes the game-time factor before
   capturing. The owner keeps SETA active through the sustained active window.
   The agent then records the same-session bridge-free SETA control window.
6. When prompted, the owner returns to normal time and performs one
   owner-controlled load/reload boundary action. The agent observes the
   recovery window without reading or modifying saves.
7. The agent checks every runner result, frame interval, full-set field and
   disposition matrix, independent SQLite readback, recovery outcome, raw
   artifact digest, and durable private locator. The owner does not need to
   restart X4 for another window unless an actual failure requires a new
   package or game process.

The accepted average-FPS floors remain 144 at normal speed and 60 in SETA. The
complete callback ceiling is derived from `1000 / 144`; the cooperative yield
target remains 2 ms. Candidate age is 30 seconds, inactivity is 10 seconds,
parent freshness is 30 seconds, and the finite admission window is 60 seconds.
No deadline is enlarged for Gate B.

## Stop and failure conditions

Stop the affected window on a missing discovered ID, unknown disposition,
applicable unsupported field, cross-faction dependency, growing steady backlog,
nonzero final backlog, freshness/deadline breach, unbounded retained state,
rejected or failed outcome, source-boundary ambiguity, or failure of the
approved FPS/callback criteria. Preserve the failure as evidence; do not retry
silently or report partial completion as success.
