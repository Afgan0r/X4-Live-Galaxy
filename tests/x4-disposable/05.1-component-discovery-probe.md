# Phase 05.1 Disposable Component Discovery Probe

## Purpose

This is a one-attempt, human-only Creative Custom procedure for the bounded
station discovery hypothesis. It records only sanitized class-level evidence.
Local implementation and fake contracts may pass, but native availability,
native cost, and owner normalization remain **pending game smoke test** until
this exact procedure records a qualifying result.

## Preconditions

- X4 is closed before extension deployment; use the approved deployment
  operation only. Do not modify vanilla files or any other extension.
- Create a new disposable X4 9.00 Creative Custom campaign. Never inspect,
  copy, load, edit, or otherwise access a save file.
- Activate only `live_galaxy` and its required support dependency. The
  telemetry opt-in is disabled by default and may be enabled only for this
  named attempt.
- Run the local package guard and Rust contract before opening X4. These are
  `verified locally`, not proof of native X4 behavior.
- Predeclare exactly one faction station scope, a raw-count hard limit, and a
  fixed per-cycle prefix. The whole returned owner-scoped result must fit the
  raw-count hard limit; do not truncate a larger result.

## Single Attempt

Use the sanitized attempt identifier
`obs-x4-component-discovery-051-01`. It contains no raw X4 identity.

1. Start one bridge attempt from the same interactive Windows account as X4.
   Record only its health class: `ready`, `unavailable`, or `failed`.
2. Launch the disposable Creative Custom scenario and run one read-only
   component discovery cycle for the predeclared faction station scope.
3. Observe one bounded result only: a complete class-level success, or one of
   `facts_unsupported`, `enumeration_unavailable`, `enumeration_overflow`,
   `facts_malformed`, or `facts_partial`.
4. Stop the bridge and append one sanitized ledger row. Do not retry, expand
   to another owner, choose another native seam, add a cursor, or widen the
   bound in this procedure.

## Stop Conditions

Stop immediately and classify the attempt as `failed` or `pending game smoke
test` if any condition occurs:

- The raw count is absent, non-integral, negative, or over the predeclared hard
  limit before any allocation, conversion, metadata, ownership, sector, or
  capacity read.
- A native count/fill or component-local read is unsupported, unavailable,
  malformed, partial, or has unbounded observable cost.
- Any completion marker is missing, any result is not the full declared
  owner-scoped scope, or a mutation signal appears.
- Diagnostics would require raw IDs, payloads, native error text, prompts, or
  hidden reasoning.

If the probe fails, retain `facts_unsupported` and route a future separately
authorized revision. Do not infer that another seam is safe.

## Evidence Boundary

Only a fresh qualifying Creative Custom run may record `observed in X4`.
Until then, all component discovery claims remain `pending game smoke test`.
The procedure has no report, acknowledgement, command, effect, persistence,
model, public UI, or game-state mutation path.
