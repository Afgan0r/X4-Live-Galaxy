## Findings

1. The available native enumeration is count-then-fill and requires allocating a
   `UniverseID[count]` buffer. It has no observed offset, cursor, page-size, or
   continuation parameter. Therefore a loop that calls the same API repeatedly
   with an invented offset cannot be treated as paging and may repeat or skip
   entries.
2. Emission paging and discovery paging are different. After a successful full
   count/fill, the bridge can split the returned IDs into deterministic frames
   (for example, at most 127 data frames plus one completion marker), but this
   does not make a large native allocation safe. The allocation itself needs a
   separately measured hard ceiling.
3. Silently taking the first 64 (or any other prefix) is not complete discovery.
   If the count exceeds the measured allocation ceiling, the correct result is a
   distinct fail-closed overflow with no component reads and no completion marker.
4. A multi-cycle strategy is only safe if a future probe establishes a stable
   ordering and a way to identify a coherent enumeration snapshot. Without that
   evidence, rescanning and deduplicating across cycles can miss additions or
   removals and must be labelled partial, not complete.

### Product-direction correction: incremental flow control

The owner explicitly prefers bounded incremental transport/consumer throughput,
not a single atomic complete faction snapshot and not an arbitrary global 64
scope ceiling. The installed X4 MCP precedent keeps pending send buffers,
bounded per-slice offer work, pipe-readiness/throttle checks, and drains pending
items over later ticks (observed). Its warehouse path also exposes a delivery
cursor and sends one event when quota permits. These patterns prove incremental
delivery is practical, but do not prove that `GetAllFactionStations` supports
native paging.

Live Galaxy can therefore separate discovery production from transport: retain a
bounded work queue, emit a bounded number of station frames per tick, expose
backlog/drain health, and stop production under backpressure. Frames need a
generation/sequence; `streaming`, `complete`, `overflow`, and `degraded` must be
distinct. Completion is safe only for a coherent verified generation. If the
queue is replaced or re-enumeration fails, retain the prior projection and omit
completion for the new generation.

This remains an inference for Live Galaxy. No offset/cursor argument is visible
in the native station API, so an invented multi-cycle prefix is not complete.
True paging or event/delta completeness needs a separate X4 evidence and
contract slice.

## Safe design boundary for the next GSD plan

The next plan should not simply raise 64 again or optimize for one atomic full
snapshot. It should first run a disposable
X4 measurement spike that records: returned count for the target faction,
allocation success at candidate ceilings, fill count consistency, elapsed game
thread time, and whether repeated calls return a stable order. The ceiling must
be selected from measured memory/time budgets and remain fail-closed above it.

The implementation should separate discovery production from transport with
bounded per-tick work, a bounded pending queue, drain/quota telemetry, and safe
backpressure. If count/fill remains the only verified native source, it may feed
that queue only when the measured allocation ceiling permits; otherwise retain
`enumeration_overflow` and do not invent offset paging. A future event/delta or
true paging design requires a separate evidence and contract slice for
generation identity, progress, restart/retry idempotency, reconciliation, and
safe completion.

## Compatibility and risks

- The installed X4 Live extension is a call-shape and performance precedent, not
  Live Galaxy authority and not code to copy.
- Bulk faction enumeration may include stations not known to the player in the
  reference extension; Live Galaxy must make visibility/ownership semantics
  explicit rather than assuming the reference's filtering is authoritative.
- Native calls and allocation cost remain unverified for a hundreds-sized scope
  in the Live Galaxy extension. The result is pending a disposable X4 9.00 run.

## Minimum verification spike

Use one default-off, attempt-scoped disposable Creative Custom probe. Query the
target faction count, exercise only measured candidate allocation ceilings, and
record sanitized count/result class, fill count, ordering stability, timing, and
bridge health. Do not retain raw IDs, payloads, saves, or native error text.

## Recommended next action

Replace the 64-station implementation boundary with a measured allocation/time
ceiling decision. Keep `enumeration_overflow` above that ceiling. Do not claim
complete arbitrary-size faction discovery until X4 evidence supplies either a
real paging contract or a measured single-call ceiling that covers the observed
scope.
