# Plan 05.1-05 Verification

## Verdict

ISSUES FOUND. The two previously reported plan defects are fixed: Task 2 now
defines same-window `t0`/`t1` counter subtraction and captures both initial and
final FIFO depth dimensions; Task 1 requires physical deletion of the legacy
sector fallback and a path-absence contract. The MCP clean-room boundary,
no-arbitrary-16/64 intent, no-acknowledgement handoff, generation-scoped
atomic admission, and validation/PATTERNS coverage are otherwise explicit.

Two blockers remain. The plan cannot deliver a complete owner scope larger than
64 stations while its own current production seams still impose hard 64-frame,
64-member, 128-frame, and 2 KiB limits, because the affected production files
are absent from `files_modified` and no task requires replacing or explicitly
re-scoping those limits. The byte-rate oracle also does not state that enqueue
and successful-write byte counters use the identical serialized-byte unit; the
inequality could therefore compare payload bytes with wire bytes and pass for
the wrong reason.

## Blockers

### 1. Existing production ceilings make the promised >64 complete scope impossible

- **Dimension:** `context_compliance` / `key_links_planned`
- **Severity:** `blocker`
- **Plan:** `05.1-05`
- **Location:** frontmatter `files_modified`; Task 1 action; Task 2 action; success criteria
- **Description:** The plan promises a complete owner generation above 64 and
  says that no 16/64 global ceiling constrains it, but the current production
  seams still reject such a stream: `crates/observation-ingest/src/batch.rs:34-40`
  defines `MAX_SCOPE_MEMBERS = 64`, `MAX_BATCH_FRAMES = 128`, and the 2,048-byte
  tracer-frame/batch budget; `crates/x4-bridge/src/server.rs:34-36,124-140`
  defines `MAX_PENDING_OBSERVATIONS = 64` and a 2,048-byte pipe-frame budget;
  `crates/x4-bridge/src/listener.rs:3-6,54-56` independently receives at most
  2,048 bytes per message. The plan modifies `server.rs` but not
  `observation-ingest/src/batch.rs` or `listener.rs`, and no action says how a
  stream of hundreds of station frames bypasses or replaces these bounds.
  A complete marker would therefore be rejected or never reach atomic
  reconciliation once the scope exceeds the existing limits. The
  `runtime_facts.rs:6,134-143` limit of 16 is per envelope and can remain a
  schema bound, but the plan must explicitly distinguish it from owner-scope
  capacity and prove the aggregate path has no arbitrary 16/64 ceiling.
- **Fix:** Add every affected production seam to the owning task's
  `files`/`files_modified` and specify the replacement contract: measured
  per-frame/schema limits remain local, while pending observation count,
  complete-scope membership, aggregate batch admission, listener receive size,
  and any batch-byte ceiling are either made compatible with the bounded FIFO
  stream or are redesigned so they cannot reject a measured >64 owner scope.
  Add a contract with more than 64 (and, if the selected envelope requires it,
  more than 128) one-station frames proving the terminal marker reaches atomic
  admission. Do not replace these with a new arbitrary constant or promote
  MCP's 256 KiB value.

### 2. Byte deltas are not defined in a comparable unit

- **Dimension:** `verification_derivation`
- **Severity:** `blocker`
- **Plan:** `05.1-05`
- **Location:** Task 1 behavior/action; Task 2 behavior/action; success criteria
- **Description:** Task 2 correctly requires snapshots at `t0` and
  `t1 = t0 + 30`, subtracts each counter, and compares message and byte
  deltas. It never defines whether `fifo_enqueued_bytes` and
  `successful_local_write_bytes` count the same canonical serialized envelope
  bytes (including or excluding exactly the same framing). If enqueue counts
  payload bytes while a pipe write counts framing bytes, the required
  `write_bytes_delta > enqueue_bytes_delta` can pass without proving that the
  consumer drained more data than the producer accumulated. This is a direct
  gap in the requested independent byte drain oracle.
- **Fix:** Define one byte-accounting unit at the protocol seam, preferably the
  exact canonical encoded frame length handed to the FIFO and handed to the
  pipe. State that both counters use that same unit, and assert the fixture and
  disposable ledger record it. Keep message counters separate and retain the
  Rust `admitted_generation_count` oracle independent of this local handoff
  rate test.

## Skill Learning

Skill learning: none — the findings apply existing project rules for bounded

## Recommendation

Revise the plan before execution. First include the existing Rust batch and
listener ceilings in the bounded-stream design and prove they cannot impose a
global 16/64/128 scope cap. Then define one comparable byte-accounting unit for
the same-window oracle. Re-run the plan checker after those two blockers are
resolved; the remaining findings are warnings only.
