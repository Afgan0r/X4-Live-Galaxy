## Slot Transition Table

| Prior slot state | Evidence or action | Turnover | Raw-byte owner after transition | Next identity |
| --- | --- | --- | --- | --- |
| Empty | Stage new identity | Pending | Pending slot | Blocked until disposition |
| Pending handoff | `Received` | Released | Released replay | Admitted |
| Pending handoff | `Committed` | Released | Released replay | Admitted |
| Pending handoff | Terminal rejection | Released | Released replay | Admitted |
| Pending handoff | `CapacityUnavailable` | Retained exact retry | Pending slot | Blocked |
| Pending handoff | `AmbiguousCommit` | Blocked ambiguous | Pending slot | Blocked |
| Ambiguous | Reconciled committed | Released | Released replay | Admitted |
| Ambiguous | Proven not committed | Retained exact retry | Pending slot | Blocked until same-request retry |
| Ambiguous | Still ambiguous or bound reached | Blocked ambiguous | Pending slot | Blocked |

An exact replay of a released identity returns its prior disposition. Changed bytes under the same identity conflict. A different identity can replace only the single released-replay owner; it cannot displace a pending or ambiguous owner.

## Prepare and Finalize Contract

1. Exact completion produces one unpublished `ValidatedSectionRevision`.
2. `prepare_publication` establishes revocable session authority without changing current revisions, pointers, history, uncertainty, or eligibility.
3. `PublishRequest` freezes source/session/section identity, revision, content digest, expected predecessor, and dependencies, and reports a checked logical retained-byte charge.
4. The repository publishes the exact request atomically.
5. Only committed-new, committed-replay, or committed reconciliation evidence calls `finalize_committed`.
6. Finalization revalidates authority generation, source session, current pointer, and frozen dependencies, then installs once or reports idempotent prior finalization.
7. Any finalization invariant failure after durable evidence keeps the attempt blocked for reconciliation; it cannot silently strengthen decision evidence.

## Application API and Ambiguity Flow

`ObservationLifecycle<R>` owns one `StopAndWaitSlot`, one `GenerationStager`, one `DecisionRevisionIndex`, one repository, and at most one `RetainedPublicationAttempt`. Its composition operations are `submit`, `reconcile_ambiguous`, and `retry_proven_not_committed`.

- `submit` runs the byte limit, strict whole-message decode, transport-epoch check, and context-variant check before constructing `ImmutableApplicationBatch` or touching the slot.
- Start and batch messages return volatile `Received`; exact completion publishes before it can return `Committed`.
- Ambiguity retains the exact typed request, attempt identity, prepared authority, timestamps, checked logical charge, reconcile count, and attempt state. Raw bytes remain only in the occupied slot.
- Committed reconciliation finalizes and releases once. Proven non-consumption changes only to retry eligibility, then republishes the same request without decode or reassembly. Still-ambiguous and age/count bounds preserve the blocked attempt.
