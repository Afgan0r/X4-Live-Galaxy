## Accepted decisions

### Observation and publication

- Independent section revisions carry capture windows, coverage, quality, availability and freshness. A decision freezes exact compatible accepted revisions; it never claims a globally simultaneous X4 snapshot.
- A bounded keyed Rust map holds at most one incomplete revision per section key, with independent per-candidate and aggregate byte/count/work/age limits.
- Freeze dependencies at candidate start. Finish privately and revalidate at commit; stale dependencies discard the candidate and trigger bounded recollection. No baseline cross-revision merge or carry-forward.
- Use a lightweight start envelope and content-bound completion. Validate contiguous section-local ordinals, counts/digests, exact schema/policy/canonicalization/digest versions, dependencies and coverage.
- One transaction binds immutable accepted content, the terminal idempotency receipt and conditional current-pointer update. Emit `committed` only after commit. Incomplete candidates remain volatile and are recollected after Rust loss.
- Keep source, producer-incarnation, transport, section, batch, record and decision identities distinct. Exact identity with exact bytes is idempotent; changed bytes under the same identity are a conflict.

### Scheduling and bounds

- Rust owns global collection policy. This phase defines the contract for X4-local continuations and final safe-step admission without implementing the production Lua/native path. Logical intent is not remote RPC for individual getters.
- One shared scheduler advances bounded persistent work on abstract delivered pulses. The selected instantiated MD cue and its observed delivery/lifecycle behavior belong to the 05.4 runtime adapter; local tests here do not claim that evidence.
- Collection scheduler and transport pump are separate state machines; pump first, reserve downstream capacity before producing new work, and never repeat getters while retrying immutable bytes.
- Game time controls urgency; real time controls admission. Apply bounded refill, burst, step count, heavy permits and overrun debt even with frozen/coarse clocks. SETA cannot multiply real-time budgets or trigger proportional catch-up.
- Prioritize core identity/ownership/location before deferrable details. Fairness is conditional on capacity; starvation appears as stale data, and missing freshness blocks dependent decisions.
- Bound native allocations/results, retained continuations, semantic records, batches, pending transport, receiver allocation, raw/decoded candidates, accepted history and diagnostics separately. Native calls remain indivisible; unsafe hitches reject the collector.
- Derive configuration values from relevant measurements. Legacy 129-member, 64-frame, 1800-byte, FIFO and borrowed 256 KiB values are not production defaults. Removing arbitrary limits never authorizes unbounded state.

### Carrier-neutral feedback contracts

- Define the Live Galaxy facade with bounded complete-message, connection, send, control-poll and error semantics. Do not implement or select a production carrier in this phase.
- Begin with one globally unacknowledged immutable application batch. Multiple sections may interleave through this single slot.
- `received` means batch validation and volatile RAM staging. `committed` means durable atomic section publication. A pipe write alone means neither.
- Preserve capacity-unavailable, exact duplicate, permanent rejection, timeout/supersession, stale epoch and ambiguous commit outcomes as separate classes. Only proven non-consumption permits retry with the same identity and bytes.
- Reserve bounded terminal/control capacity. Inbound traffic contains small handshake, demand, disposition, collection intent, health and reset records, never bulk observations, raw model output or complete plans.
- An oversized inbound message must fail closed as a whole; do not reconstruct it by assuming raw error fragments contain all original bytes.
- Reconnect discards volatile candidates. Exact terminal replay uses the durable receipt; ambiguous state is never continued as if receipt were proven.
- The 2026-09-04 Docs MCP evidence demonstrated the Carrier B trigger: Carrier A cannot prove bounded nonblocking writes or typed short-write/error outcomes. Carrier B implementation and X4 lifecycle proof therefore belong to dedicated Phase 05.4. A fixed window, dynamic credit and durable per-batch staging remain separately evidence-triggered extensions.

### Source uncertainty and lifecycle

- Source membership, producer assembly, transfer and publication completeness are independent. A correct certificate cannot promote `partial_set` or count/fill observations to `complete_set`.
- Unknown source epoch is an accepted baseline: a local producer incarnation fences one uninterrupted unambiguous runtime scope. The generic contracts invalidate unfinished work and previous current decision eligibility when the adapter reports start/load/reload uncertainty; runtime detection belongs to 05.4 and does not invent a campaign UUID.
- Complete-set absence and entity deletion require qualifying source coverage, stable identity and the same authoritative scope. Two consecutive qualifying absences may remove; partial or failed scans have no absence meaning. Optional field failure never deletes the core entity.
- Automatic save pause/resume remains unsupported because the current evidence does not establish a safe save-begin or durability boundary. This phase defines no numeric cooldown; any later runtime behavior must be discussed and proven in 05.4.
- Event/delta mode requires an authoritative source boundary, contiguous ordered events and gap/retention semantics. It is deferred, not an alternative inferred from repeated polling.
