## Narrative Findings (AI reviewer)

### P1 / BLOCKER — CR-10: Publication accepts a stale session when the caller repeats its identity

**File:** `crates/observation-persistence/src/types.rs:42-52`,
`crates/observation-persistence/src/record.rs:12-20`,
`crates/observation-persistence/tests/port_contract.rs:146-172`

**Issue:** `PublishRequest::from_revision` accepts an arbitrary
`authoritative_session` argument, and normalization proves only that this
caller-supplied value equals the session already embedded in the revision.
The repository stores no current source-session authority and receives no
unforgeable acceptance result from `DecisionRevisionIndex`. After a reconnect,
a delayed revision from the old producer/epoch can therefore be committed by
constructing the request with
`delayed.source_session().clone()` as both the revision identity and the claimed
authority. Its unchanged predecessor and dependency checks pass, so SQLite can
advance the durable current pointer using history-only evidence.

The regression at `port_contract.rs:146-172` passes the new session explicitly
and proves only that an honest caller supplies the expected mismatch. It does
not exercise the public request construction that repeats the delayed
revision's old session, which passes `record::normalize` by construction.
This leaves the accepted phase rule that source/load uncertainty makes prior
revisions history-only dependent on caller discipline at the durable authority
boundary.

**Fix:** Make current source-session authority repository/application state
rather than request data, or make publication consume an opaque accepted token
that only `DecisionRevisionIndex::accept` can produce. Compare the revision's
session with that trusted current authority immediately before the publication
transaction. Add a regression that validates under session A, marks session B
authoritative, then attempts publication while repeating session A in every
caller-controlled request field; it must not create content, receipt, or a
current pointer.
