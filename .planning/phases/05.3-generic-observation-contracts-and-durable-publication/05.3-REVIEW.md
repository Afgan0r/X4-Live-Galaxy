# Phase 05.3: Code Review Report

## Narrative Findings (AI reviewer)

### P1-01 (BLOCKER): Completion certifies receiver-derived state instead of sender-declared content

**Locations:** `crates/observation-ingest/src/wire.rs:81-91`, `crates/observation-domain/src/observation.rs:161-170`, `crates/observation-ingest/src/generation.rs:158-166`, `crates/observation-ingest/src/completion.rs:68-84`, `crates/observation-ingest/src/completion.rs:155-175`

**Observable failure:** A producer can send two distinct batches in the wrong order and then send the same completion envelope. The receiver assigns fresh contiguous ordinals from arrival order, calculates batch count, byte counts, manifest digest, content digest, and all four contract versions from its own staged candidate, then compares those values back to that same candidate. The completion is accepted even though the producer never declared the batch order or any of those certificate values.

**Concrete evidence:** `RawBatch` has no section-local ordinal and `RawCompletion` contains only identity, `record_count`, and coverage. `completion_certificate` fills every supposedly content-binding field from `candidate`; `completion_is_exact` therefore proves only internal self-consistency. The rejection test at `crates/observation-ingest/tests/completion_contract/rejections.rs:3-16` mutates a certificate after the receiver generated it and does not exercise a malformed wire certificate. This breaks the locked content-bound completion and out-of-order rejection contract at the untrusted-input boundary.

**Smallest viable fix:** Add a producer-declared section-local ordinal to each immutable batch and producer-declared batch count, raw/decoded lengths, ordered manifest digest, canonical content digest, and exact schema/policy/canonicalization/digest versions to the completion wire type. Keep the private calculation, but compare it against the decoded sender certificate. Add wire-to-completion regressions for reversed, missing, duplicated, and changed ordinals and for each mismatched count, digest, length, and version.

### P1-02 (BLOCKER): Monotonic revision and entity versions are not enforced after a real commit

**Locations:** `crates/observation-ingest/src/generation.rs:9-31`, `crates/observation-ingest/src/candidate_limits.rs:137-153`, `crates/observation-ingest/src/candidate_limits.rs:173-199`, `crates/observation-application/src/lifecycle_publication.rs:122-132`, `crates/observation-persistence/src/fake.rs:48-78`, `crates/observation-persistence/src/sqlite_write.rs:58-79`

**Observable failure:** After publishing entity version 2, a later section can publish version 1 for the same `(source_scope, entity)` because the production lifecycle never updates `GenerationStager.accepted_versions`. Separately, a current section revision 5 can be replaced by a previously unused revision 3 when the request names revision 5 as `expected_current`; both repositories validate pointer equality but never require the proposed revision to advance.

**Concrete evidence:** The sole accepted-entity mutator is `record_accepted_entity`. Structural usage/caller discovery found only test callers at `crates/observation-ingest/tests/keyed_candidates.rs:154` and `crates/observation-ingest/tests/completion_contract/rejections.rs:25`; no production call records committed entities. `finish_committed` finalizes the decision index but does not update the stager. Repository preflight accepts any non-conflicting revision identity after the expected-pointer check, with no ordering comparison. The current tests manually seed the version map and test isolated CAS behavior, so the complete application path does not cover the regression.

**Smallest viable fix:** Make one committed, authoritative monotonic-version source feed both staging and restart recovery. On definitive commit/finalization, record every accepted entity version and digest, and require the proposed section revision to be greater than its expected current revision (except exact replay of that same durable revision). Add an application-level sequence that commits entity/revision 2, rejects entity/revision 1, rejects equal-version changed content, and accepts version 3.

### P1-03 (BLOCKER): Durable revisions cannot restore typed eligibility evidence after restart

**Locations:** `crates/observation-persistence/src/record.rs:30-45`, `crates/observation-persistence/src/types.rs:34-49`, `crates/observation-persistence/src/sqlite_read.rs:44-104`, `crates/observation-persistence/src/port.rs:9-23`

**Observable failure:** After reopening SQLite, callers can load records, coverage, dependencies, and an opaque debug string, but cannot reconstruct the capture window, freshness, quality, availability, stable-identity evidence, or exact contract versions needed by `ValidatedSectionRevision` and `DecisionRevisionIndex`. A committed current revision therefore cannot become a typed immutable decision input after process restart without recollection or ad-hoc parsing of a compiler-generated debug representation.

**Concrete evidence:** `normalize` serializes the entire candidate context with `format!("{:?}", revision.context())`. `RevisionRecord` exposes only `context_token: String`; `load_revision` returns that string unchanged, and the repository port has no typed hydration API. Debug formatting is neither a stable persistence schema nor a parser-supported contract. The restart tests prove that rows and receipts survive, but do not rebuild decision eligibility from a reopened repository. This contradicts durable publication to immutable decision inputs and exact preservation of the independent OBS-03 evidence axes.

**Smallest viable fix:** Persist the context as versioned typed columns or a canonical versioned payload, validate every field on read, and expose a bounded hydration path that rebuilds the current decision index and committed entity-version state. Add a close/reopen test that establishes eligibility before shutdown and proves the identical eligibility set, blockers, evidence axes, and version fences after reconstruction.

### P1-04 (BLOCKER): Exact replay of a historical revision is reported as currently committed

**Locations:** `crates/observation-persistence/src/fake.rs:33-43`, `crates/observation-persistence/src/fake.rs:48-58`, `crates/observation-persistence/src/sqlite_write.rs:58-71`, `crates/observation-application/src/lifecycle_publication.rs:102-132`, `crates/observation-ingest/src/eligibility/authority.rs:103-130`

**Observable failure:** Publish revision 1, advance the same section to revision 2, then replay the exact revision-1 request. Both repositories return `CommittedReplay` before checking that revision 1 is still the durable current pointer. The application treats that as current durable authority. With a live index it falls into `FinalizationBlocked` and retains a permanently blocked attempt; with a newly constructed empty index it can finalize revision 1 as decision-current even while SQLite points to revision 2.

**Concrete evidence:** Fake `replay` and SQLite `publish_in_transaction` classify equality of the immutable historical row as committed replay without comparing `current_revisions` to the replayed revision. `finish_committed` then always attempts decision-index finalization. The current-pointer guard in finalization compares only the in-memory pointer to the revision's old `expected_current`; it is not proof of the repository's current pointer, especially after restart. Existing replay tests cover a revision that is still current, not historical replay after a successor.

**Smallest viable fix:** Define terminal replay as exact row plus exact receipt plus durable current pointer equal to the replayed revision. Return a definitive stale/superseded outcome for an exact historical row and make reconciliation able to classify the same state without remaining ambiguous. Add fake, SQLite, application, and reopen regressions for `rev1 -> rev2 -> replay rev1`.

### P2-01 (WARNING): Stop-and-wait replay identity omits semantic lifecycle context

**Locations:** `crates/observation-application/src/types.rs:6-43`, `crates/observation-application/src/lifecycle.rs:39-52`, `crates/observation-application/src/lifecycle.rs:109-126`, `crates/observation-ingest/src/feedback/slot.rs:8-31`, `crates/observation-ingest/src/feedback/slot.rs:102-120`

**Observable failure:** Re-submit the same outer `BatchId`, epoch, and raw start/completion bytes with a changed `CandidateContext` or `CompletionCurrent`. The slot returns the previous disposition as an exact replay before dispatch, even though the new call carries different dependencies, expected pointer, evidence axes, or contract versions. The caller receives `Received`/terminal success for semantic input that was never processed.

**Concrete evidence:** `LifecycleInput` makes context part of the application request, but `ImmutableApplicationBatch` retains only epoch, identity, and bytes. `validate_context` checks only the enum variant and transport epoch. `stage_batch` therefore classifies replay without comparing the sideband values. This is a replay/idempotency robustness defect even if Phase 05.4 later supplies the context from a trusted local adapter.

**Smallest viable fix:** Bind a canonical digest of the relevant lifecycle context into the immutable application-batch replay identity, or reject changed sideband before replay classification. Add exact-replay tests that vary each start and completion context field and require an identity conflict with no state mutation.

## Review Coverage and Evidence

- **Security and trust boundary:** Strict JSON decoding uses `deny_unknown_fields`, applies the outer byte limit before typed construction, and rejects invalid identifiers and contract version. P1-01 leaves the decisive completion authority receiver-generated rather than sender-bound; P2-01 omits semantic sideband from replay identity. No hard-coded secret, unsafe Rust, command injection, path traversal, or raw rejected-payload logging was found.
- **Atomicity:** SQLite content, receipt, and current-pointer installation share one immediate transaction; pre-commit failpoints roll back. Decision-index finalization follows committed-new/replay evidence. P1-04 shows that the replay evidence is too broad for historical rows, and P1-03 prevents restoration of the same typed authority after restart.
- **Idempotency and replay:** Exact current publication replay and ambiguous retained-request retry are byte/identity stable in covered tests. P1-04 and P2-01 are uncovered cross-state replay failures.
- **Ambiguous commit recovery:** The durable ambiguity barrier is installed before publication and survives restart; reconciliation checks stored row, receipt, pointer, dependencies, and corruption before clearing it. The reviewed single-owner path does not retry an unresolved attempt. Historical exact rows need the definitive stale classification described in P1-04.
- **Checked resource accounting:** Candidate and aggregate counters use checked add/release; message, candidate, aggregate, scheduler, retained-attempt, repository, diagnostic, and retention limits are finite and injected. Scheduler debt saturates only at its explicit rejection ceiling and deterministic tests cover frozen/coarse clocks. No unchecked overflow that can authorize excess work was found.
- **Deterministic ordering:** `BTreeMap`/sorted record material, canonical dependency ordering, urgency/class/FIFO queue tie-breaking, receipt ordinals, and decision identities are deterministic. P1-01 means the batch manifest's order is deterministic only after the receiver invents it, not relative to producer-declared section order.
- **Regression and mutation evidence:** `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets --all-features -- -D warnings`, and `cargo test --workspace --all-targets` passed at the review tree. Passing tests do not cover the five scenarios above. The recorded absence of `cargo-mutants` is the plan-approved availability result and is not itself a defect; consequently there is no mutation evidence for these state-machine boundaries. No X4 runtime behavior was implemented or required in this phase.
