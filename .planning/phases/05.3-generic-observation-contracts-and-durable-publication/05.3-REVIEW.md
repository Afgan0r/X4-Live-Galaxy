# Phase 05.3: Code Review Report

## Narrative Findings (AI reviewer)

### P1 / BLOCKER — CR-01: Candidate identity drops producer incarnation and transport epoch

**Location:** `crates/observation-ingest/src/generation.rs:76-109`, `crates/observation-ingest/src/generation.rs:113-141`

**Observable failure:** A second `SectionStartEnvelope` with the same source, section key, and revision but a different `producer_incarnation`, `transport_epoch`, or `expected_records` returns `Received`. The candidate stores none of the producer/epoch fields, and subsequent batch admission has no epoch to check. Work from a stale or reconnected producer can therefore continue an existing candidate and reach completion instead of returning `StaleEpoch` or an identity conflict.

**Evidence:** `start_section` defines equality only as `source_scope == source_scope && revision == section_revision` at lines 78-82. The inserted `Candidate` at lines 97-109 omits both start-envelope fencing identities. `stage_section_batch` checks only scope and revision at lines 126-129. Existing lifecycle tests vary neither identity.

**Smallest viable fix:** Store `ProducerIncarnationId`, `TransportEpoch`, and the full immutable start identity in `Candidate`; require every batch/completion admission to arrive through an epoch-fenced session context and compare it before replay, version, or capacity checks. Treat a same revision with changed start metadata as a terminal conflict and add changed-incarnation/changed-epoch regressions.

### P1 / BLOCKER — CR-02: Batch replay identity is not bound to the decoded envelope

**Location:** `crates/observation-ingest/src/generation.rs:113-168`, `crates/observation-ingest/src/completion_digest.rs:6-18`

**Observable failure:** `stage_section_batch` accepts a decoded `ImmutableBatchEnvelope` and independent caller-supplied `canonical_bytes`. Replay compares only the SHA-256 of those external bytes. Reusing the same `BatchId` and bytes with changed decoded records returns `Received` as an exact replay, while equivalent envelopes accompanied by different bytes conflict. The stored envelope and the manifest digest are consequently not guaranteed to describe the same message.

**Evidence:** The digest is calculated solely from `canonical_bytes` at lines 121-122 and replay exits before comparing the envelope at lines 131-138. `StagedBatch` stores the separately supplied envelope with that digest at lines 157-163. Completion later trusts both as one batch and hashes the stored records independently, but never proves that the manifest bytes decode to those records.

**Smallest viable fix:** Make one representation authoritative. Prefer accepting bounded raw bytes, decoding once, and retaining the exact bytes plus decoded envelope; alternatively compute a versioned canonical encoding internally from the envelope. Exact replay must compare a digest covering every envelope field and the retained bytes. Add a same-ID/same-bytes/changed-envelope regression.

### P1 / BLOCKER — CR-03: Weak completion coverage can become decision-eligible

**Location:** `crates/observation-ingest/src/completion.rs:102-118`, `crates/observation-ingest/src/eligibility.rs:184-200`

**Observable failure:** Completion copies `certificate.envelope.coverage` into the validated revision without checking it against `CandidateContext.state().coverage()`. Eligibility then ignores `revision.coverage()` and checks only the context state. A `Partial`, `Unknown`, or `Unsupported` completion paired with a previously `Complete` context can therefore be frozen into an eligible decision revision. `KnownEmpty` is likewise not required to have zero records at completion.

**Evidence:** `completion_is_exact` validates counts, digests, and versions but contains no coverage/state consistency check. The constructed revision takes envelope coverage at line 114. `evidence_qualifies` reads only `revision.context().state()` and never reads the terminal coverage. Current tests exercise only matching `Complete`/`Complete` and `KnownEmpty`/`KnownEmpty` fixtures.

**Smallest viable fix:** Validate a monotone evidence relation at completion: terminal coverage must not be weaker or inconsistent with the frozen source evidence, and `KnownEmpty` must require zero records plus qualifying stable source proof. Eligibility should evaluate the validated terminal coverage (or a single normalized evidence value) rather than a parallel context field. Add a cross-product regression for all coverage values.

### P1 / BLOCKER — CR-04: Stored terminal receipts are not integrity-checked

**Location:** `crates/observation-persistence/src/sqlite.rs:120-141`, `crates/observation-persistence/src/sqlite_read.rs:92-110`, `crates/observation-persistence/src/sqlite_write.rs:65-76`

**Observable failure:** A receipt row whose `content_digest` or `previous_revision` is changed to another well-formed value passes repository open. `current()` and exact replay then return the tampered receipt as durable authority. This breaks the promised binding among immutable content, terminal receipt, and pointer even though revision-content corruption is detected.

**Evidence:** `validate_stored_revisions` checks only that `load_receipt` returns `Some`; it never compares receipt fields with the loaded revision. `load_receipt` validates shapes/ranges but has no integrity comparison. The replay path returns that receipt whenever the immutable revision record matches. Schema tests mutate `revisions.content_digest` or delete receipts, but never mutate a syntactically valid receipt.

**Smallest viable fix:** During open/recovery and before replay, require receipt section/revision/digest/previous to equal the normalized revision identity, content digest, and expected predecessor. Include receipt fields in an independently recomputable integrity binding or validate the exact tuple explicitly. Add corruption fixtures for receipt digest and predecessor tampering.

### P1 / BLOCKER — CR-05: Ambiguous reconciliation can acknowledge a different revision record

**Location:** `crates/observation-persistence/src/sqlite.rs:74-104`, `crates/observation-persistence/src/record.rs:48-57`, `crates/observation-persistence/src/record.rs:73-94`

**Observable failure:** `reconcile_publication` classifies `CommittedReplay` using only current section revision and record-content digest. A request with the same section/revision/records but changed source scope, coverage, dependencies, expected predecessor, manifest digest, or evidence context has the same content digest and can be acknowledged as the committed request. Normal fake/SQLite replay correctly compares the full normalized `RevisionRecord`, so crash reconciliation violates the shared port contract.

**Evidence:** The committed branch at lines 88-92 compares only `current == candidate.revision` and `receipt.content_digest == candidate.content_digest`. `content_digest` covers only record fields. The remaining publication-authority fields are covered by `integrity_digest`, but reconciliation neither loads nor compares the stored `RevisionRecord` with `candidate`.

**Smallest viable fix:** Load the stored revision and require full normalized-record equality plus an exact validated receipt and pointer before returning `CommittedReplay`. Return conflict or remain ambiguous for any mismatch. Add an ambiguous-cut regression that changes each non-content authority field while preserving records.

### P2 / WARNING — WR-01: Real commit ambiguity does not activate the retry barrier

**Location:** `crates/observation-persistence/src/sqlite.rs:53-71`, `crates/observation-persistence/src/sqlite.rs:146-157`, `crates/observation-persistence/src/sqlite_write.rs:37-50`

**Observable failure:** The test-only `publish_with_failpoint` records an ambiguous identity in memory, so an immediate retry is blocked. The normal `ObservationRepository::publish` path returns `Ambiguous` when `transaction.commit()` errors but never inserts that identity into `self.ambiguous`; the next call can immediately enter publication/replay instead of requiring explicit reconciliation. Reopening also starts with an empty ambiguity set.

**Evidence:** Lines 68-70 update the barrier only in `publish_with_failpoint`. The trait implementation at lines 146-157 delegates and returns without inspecting the outcome. Existing tests cover only failpoint-generated ambiguity.

**Smallest viable fix:** Route both paths through one helper that records every ambiguous outcome before returning. Define restart behavior explicitly: either persist pending ambiguity identities or require an exact reconciliation API before ordinary publication/replay can acknowledge the attempt. Add a backend-injected commit-error regression through the normal trait method.

### P2 / WARNING — WR-02: `receipt_count` is applied per section, not as a repository bound

**Location:** `crates/observation-persistence/src/retention.rs:15-31`, `crates/observation-persistence/src/retention.rs:58-73`

**Observable failure:** `RetentionPolicy.receipt_count` never limits total retained receipts. It is folded into a per-section `keep` value, and `seen` is keyed by `SectionKey`. With many section keys, each section retains up to that many historical receipts, so repository receipt/history growth is not bounded by the configured receipt count.

**Evidence:** `keep = min(history_per_section, receipt_count - 1)` is calculated once, but victim selection increments a separate counter per section. The only retention test publishes one section and cannot reveal global overflow.

**Smallest viable fix:** Enforce two independent policies: retain at most `history_per_section` unprotected histories per section, then apply a deterministic global `receipt_count` cap across all unprotected receipts while preserving current, dependency-reachable, and pinned revisions. Add exact/one-over tests spanning more than one section.
