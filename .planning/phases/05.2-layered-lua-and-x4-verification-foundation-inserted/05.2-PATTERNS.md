Every plan action must name its applicable analogue rather than relying only on
this routing table. Deviations must state why the analogue is insufficient and
which invariant remains preserved.

The candidate matrix owns deterministic build partition metadata. Candidates
may share a generated build only when their content/UI registration,
entrypoint/import root, and native-binding acquisition produce the same
`build_profile_digest` and neither candidate declares a loader/registration
conflict. Any candidate changing loader or registration is exclusive and gets
its own build group and generated root. Build groups and members are sorted by
stable ID; undeclared, asymmetric, or same-group conflicts are rejected.

The pure runner emits versioned JSONL conforming to
`tools/x4-verification/contracts/runtime-evidence.v1.json`. The builder emits a
machine-local `manifest/build-manifest.v1.json` per generated root, validated
by `candidate-build-manifest.v1.json`. Retention consumes both interfaces and
emits only the sanitized ledger contract.

## Inherited execution boundaries

- X4, installed extensions, and saves are not execution inputs for this phase.
- The public `extensions/live_galaxy` package receives no candidate control or
  verbose trace module. Candidate build output is generated outside that tree.
- Local fakes and standalone Lua are `local-contract-only`; package conformance
  is `packaged-static`; neither is `observed-in-X4`.
- Phase 05.1 source-level defects, including incompatible aggregate ceilings or
  incomparable byte counters, are not runtime candidates. They remain explicit
  source-action prerequisites owned by Phase 05.1.
- No new external package is required. Existing PowerShell, the pinned Lua 5.1
  runner, and the current Rust workspace commands are sufficient.
