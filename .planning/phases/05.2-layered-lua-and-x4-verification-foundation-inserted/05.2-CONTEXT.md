# Phase 05.2: Layered Lua and X4 Verification Foundation — Context

## Phase Boundary

Build the reusable admission and read-only experiment foundation that must exist
before Phase 05.1 performs another X4 run. This phase does not execute X4,
change the Phase 05.1 production seam, or introduce game mutation.

## Locked Decisions

### Admission ownership

- Source collection fills dossier fields and reports evidence, conflicts, and
  unknowns; it cannot issue PASS or BLOCK.
- Independent planning and verification gates decide whether dossier and
  known-failure coverage are sufficient.
- No seam, including a small change, bypasses the registry automatically.
- An owner override is explicit, scoped, reasoned, and records remaining risk.

### Dossier and registry

- The dossier is phase-owned, versioned, machine-checkable, and cites both a
  primary source and a verified working production precedent.
- Required dimensions are loader/registration/module resolution, Lua/native
  binding, calls and returns, native/canonical identity, lifecycle/thread/
  cadence/reconnect, failure/partial/completeness, and volume/performance.
- Each field is `EVIDENCED`, `CONFLICTING`, or `UNKNOWN`; unresolved
  source-answerable questions block admission rather than becoming game probes.
- The initial registry contains the seven demonstrated Phase 05.1 failure
  classes named in 05.2-SPEC.md. Every class has a negative fixture that proves
  the gate rejects it.

### Conformance

- Conformance follows the actual packaged production import graph and
  extension-relative module resolution.
- Test-only loading remains available for pure/local tests but is explicitly
  classified and cannot prove packaged X4 loadability.
- Existing repository test entry points should be extended rather than replaced
  unless research proves they cannot express the required production behavior.

### Candidate experiments

- Candidate definitions are declarative, bounded, deterministically ordered,
  and source-derived.
- Compatible candidates share one developer-only build and run serially in
  isolation; loader or registration conflicts use separate builds.
- One candidate's failure cannot suppress later candidates.
- Verdicts remain three-dimensional: execution, contract, and effect.
- A valid but unexpected result is an effect mismatch, not a pass.
- Full structured JSONL stays machine-local; committed artifacts retain only
  sanitized identity, digest, evidence summary, and disposition.

### Phase 05.1 hand-back

- Remaining Phase 05.1 native, lifecycle, and transport unknowns become the
  first candidate matrix.
- Phase 05.2 prepares but does not execute that matrix.
- Phase 05.1 later owns one prepared human X4 run and its observed verdicts.
