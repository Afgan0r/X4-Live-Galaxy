## Critical Issues

### CR-01 (P1/BLOCKER): Coordinated generated-Lua and manifest forgery still publishes PASS

**Files:** `tools/x4-verification/run-candidate-package.ps1:19-28,322-355`,
`tools/x4-verification/build-candidate-extension.ps1:337-410`,
`tools/x4-verification/tests/candidate_package_adversarial.ps1:124-162`

**Issue:** The new independent repository comparison covers only dispatcher,
adapter, attestation, worker, launcher, protocol, runtime schema, and owner-root
files. It does not anchor `content.xml`, `ui.xml`, the X4-loaded generated Lua
entrypoint, or `live_galaxy_candidate_runner.lua`. Their digests remain declared
only in the caller-writable `generated_files` array. For the entrypoint, the
dispatcher also trusts a caller-recomputed `package_conformance.graph_digest`
and `package_conformance_digest`.

An independent black-box probe appended valid Lua
`error('coordinated forged entry executed')`, recomputed the entrypoint's
`generated_files` row, graph digest, and package-conformance digest, restored
owner-only ACLs, and invoked the repository dispatcher. It exited 0, returned
`verdict=pass` and `local_process_ready=true`, and published JSONL evidence. A
second probe changed `live_galaxy_candidate_runner.lua` and its manifest row;
that also exited 0 and published PASS. Thus the fix blocks the exact adapter
attack in the test but not the same attack class against other packaged code.

**Fix:** Authenticate the complete build manifest outside the generated root,
or independently derive every generated executable/package byte from committed
repository inputs before publication. At minimum, compare the runner with its
repository source and reconstruct content, UI, and entrypoint bytes from the
committed templates plus validated build identities. Add coordinated entrypoint
and runner mutations that recompute every self-declared digest and assert no
evidence or attestation artifact is published.

## Warnings

### WR-01 (P2/WARNING): The generated dispatcher advertised in each package is guaranteed to reject that package

**Files:** `tools/x4-verification/build-candidate-extension.ps1:338,416-422`,
`tools/x4-verification/run-candidate-package.ps1:280-287`,
`tools/x4-verification/tests/candidate_package_runtime_contract.ps1:10-13,103-113`,
`tools/x4-verification/tests/candidate_package_adversarial.ps1:4-17`

**Issue:** The builder copies `run-candidate-package.ps1` into every generated
root and declares that root ready, but readiness is tested with the repository
copy. Production dispatch explicitly rejects any dispatcher whose path is
inside `GroupRoot`. Both focused suites also invoke only the repository copy,
so they never exercise the packaged command.

An independent build followed by invocation of
`<group>/tools/x4-verification/run-candidate-package.ps1` exited 1 with
`UNTRUSTED_DISPATCHER_ORIGIN` and created no evidence. The generated package is
therefore not runnable through the command it ships; its passing readiness
status proves a different call chain.

**Fix:** Make the repository-fixed dispatcher the explicit sole entrypoint and
stop shipping the package-local copy as an executable command, or replace it
with a non-authoritative launcher that can only reach the fixed repository
dispatcher without caller-selected trust paths. Add a black-box test for the
exact command exposed to the human handoff.

### WR-02 (P2/WARNING): Candidate adapters ignore a caller's smaller work-unit budget

**Files:** `tools/x4-verification/candidate-adapters.psm1:57-70,116-153`,
`tools/x4-verification/tests/candidate_package_runtime_contract.ps1:66-92`

**Issue:** `MaxWorkUnits` is checked only against the adapter's maximum. The
identity adapter always returns four work units, and the volume adapter returns
`sample_count`, even when the caller supplied a smaller positive budget.
Independent calls with `MaxWorkUnits=1` returned `status=completed` with four
and seven work units respectively. The external worker later rejects such an
over-budget response, so the current dispatcher fails closed, but the exported
adapter API violates its own bound and turns valid bounded requests into a
late protocol failure. Existing alternate-valid tests always pass 16 and cannot
detect this defect.

**Fix:** Compute required work before completion and reject with
`adapter-input-invalid` or a specific budget code when it exceeds
`MaxWorkUnits`. Add identity and volume cases with a valid fixture and a budget
one below the derived work requirement; assert no completed over-budget result
is returned.
