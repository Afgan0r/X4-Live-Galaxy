# Phase 05.2 Research: Layered Lua and X4 Verification Foundation

Status: `INCOMPLETE_FOR_REVIEW`

This dossier is research input for an independent planning/verification gate. It
does not issue `PASS` or `BLOCK`. The status is intentionally incomplete:
source-resolvable native X4 signatures/returns remain unavailable in the local
installation, while embedded Lua/support-loader behavior is now substantially
resolved from installed binaries and readable support source. Runtime-only
questions remain around native call context, count/fill snapshot semantics,
and merged mod effects. Static contracts and fake adapters must not be promoted
to in-game proof.

## Scope and method

The phase goal is a reusable, fail-closed verification foundation for future
Lua, Mission Director, native-binding, and X4 adapter seams. The evidence was
collected from the current Live Galaxy checkout, the X4 Live MCP reference
checkout, the installed X4 9.00 tree, installed extension manifests and loose
files, and the completed Phase 05.1 artifacts. No save was read, X4 was not
started, and no installation, installed extension, runtime state, or reference
checkout was modified.

Evidence labels used below:

- **Documented**: stated by a repository document, manifest, or readme.
- **Observed**: recorded from an existing disposable X4 run or executable
  contract; the run's exact scope is stated rather than generalized.
- **Inferred**: a design conclusion supported by evidence but not itself an X4
  runtime observation.
- **Unknown**: not established by the available source or run evidence.
- **Conflicting**: sources disagree or a stronger source narrows an earlier
  assertion.

## Executive findings

1. **The production loader contract is extension-relative.** Live Galaxy's
   entrypoint is registered through `ui.xml` and loaded with
   `Register_OnLoad_Init`; its transitive imports use
   `live_galaxy/lua/<module>`. An earlier disposable run observed bare
   `require("live_galaxy_x4_discovery")` and then bare telemetry imports fail
   under the packaged X4 search path. The local runner deliberately adds
   test-only paths, so passing local tests does not establish packaged loading.
2. **The closest production precedent is X4 Live MCP.** It obtains `ffi.C`,
   imports the Mod Support named-pipe adapter, registers events and an on-load
   initializer, and bounds queue, retry, payload, cadence, and station-scan
   work. Its call shapes are useful precedent, not vanilla API documentation.
3. **Phase 05.1 provides good contract scaffolding but incomplete runtime
   proof.** Pure Lua, fake-adapter, source-text, and package guards exercise
   malformed counts, duplicate/foreign identity, capacity failures, no-marker
   behavior, and payload limits. Existing X4 runs observed an Argon enumeration
   overflow and later `facts_unsupported`; they did not establish native
   availability, owner closure, ordering, or a complete enumeration.
4. **The seven locked failure classes are all actionable as executable gate
   seeds.** Each class has an existing incident or contract gap and a negative
   fixture proposal below. A complete dossier validator must require an
   independent source/evidence entry for every class, not merely a prose claim.
5. **Installed compatibility evidence is partial.** KUDA AI Tweaks, More AI
   Economy Ships, and Add More Sectors are installed and have manifest-level
   metadata only because their payloads are in `.cat/.dat`. Faction Enhancer
   modules are also installed; project policy excludes that suite from the
   first public alpha. Manifest presence does not prove a runtime conflict or
   coexistence.

### Important evidence conflict: Lua version

The installed root contains `lua51_64.dll`; binary strings identify both LuaJIT
and Lua 5.1, plus FFI and standard loader/call symbols. This resolves the
embedded engine family to the installed LuaJIT/Lua 5.1 runtime, but not every
JIT extension or game-side wrapper feature. The disposable probe's note that
`_VERSION` was not exposed is therefore a probe-surface limitation, not a
contradictory engine identity. The standalone runner version in
`tools/lua-runner.lock.json` remains a test-tool choice and cannot prove
embedded behavior.

### Gap-closure source audit

The installed support archive is not opaque for the relevant Lua-loader
questions. Its `ext_01.dat` contains readable concatenated XML/Lua, and the
following exact source was inspected:

- `sn_mod_support_apis/ext_01.dat` lines 1–39 define the support add-on load
  order. `ui/lua_loader.lua` is loaded first, generic interfaces follow, named
  pipes are loaded before `ui/time/pipe_time.lua`, and `ui/external_interface.lua`
  is loaded last. This is source evidence for registration order within the
  support add-on, not a guarantee of the global order between unrelated mods.
- The same file lines 7078–7360 implement the loader. UI-added Lua is loaded
  before game initialization; `Register_Require_Response` stores a module
  response, `Register_OnLoad_Init` appends an init tuple, and
  `Register_Require_With_Init` stores both. The patched `require` returns a
  registered response or falls back to the original require. `Send_Ready` is
  one-shot, runs registered init functions in insertion order under `pcall`,
  and clears the init list. The loose loader prepends `?.txt` and `?.lua` to
  `package.path` on each load, deduplicates file loads, and raises
  `Lua_Loader.Loaded`; its own comments document duplicate-loader and repeated
  signal hazards. This resolves protected-UI require patching and support-loader
  ordering at the support implementation level.
- `sn_mod_support_apis/ext_01.dat` lines 10298–10440 and 10586–10620 show the
  named-pipe module's FFI setup (`typedef uint64_t UniverseID` and
  `GetPlayerID(void)`) and document that UI/game reload destroys queued
  requests and open pipe handles. Lines 11240–11410 show the raw read/write
  calls, `pcall` wrappers, one retry, and the distinction between an empty pipe,
  partial `ERROR_MORE_DATA` reads, and hard errors. These are support transport
  call/return semantics, not the signatures of the target X4 universe calls.
- `sn_mod_support_apis/ext_01.dat` lines 7449–7455 independently uses
  `ffi.cdef` with `int64_t GetCurrentUTCDataTime(void)`, confirming the support
  convention of declaring C symbols before calling through `ffi.C`.

## Known-failure registry seed

Phase 05.2 R2 locks seven classes. Each registry entry should contain the
evidence IDs, source provenance, executable check, and one negative fixture that
must make the gate fail. The fixtures below are design seeds, not completed
verification verdicts.

### 1. Loader mismatch

- **Evidence:** Existing X4 run in `tests/x4-disposable/01-probe-evidence.md`,
  Plan 01-10 loader follow-up: packaged X4 searched for
  `extensions/live_galaxy_x4_discovery.lua` when a bare require was used,
  while the file was under `extensions/live_galaxy/lua/`; telemetry then failed
  the same way. Current runtime and X4 Live MCP use extension-relative names.
- **Negative fixture:** remove the extension-relative prefix from a nested
  import, or point `ui.xml` at a non-existent entrypoint. The package resolver
  must fail even if the local runner's extra search path can load it.
- **Gate check:** parse manifest/UI, resolve the transitive graph under an
  installed-like root, reject bare production imports, and require the runtime
  registration symbol.

### 2. Native-binding assumptions

- **Evidence:** Static binding contracts assert `ffi`, `ffi.C`, count/fill,
  `UniverseID` allocation, and capacity calls; local fakes implement those
  assumptions. Existing X4 capability evidence reports `sector_capacity` as
  `call_error` and later `facts_unsupported`, so static source is not runtime
  proof.
- **Negative fixture:** replace `ffi.C.GetAllFactionStations` with a missing
  symbol, swap argument order, return a non-numeric count, or make the protected
  call throw. A source-only assertion must not pass.
- **Gate check:** separate acquisition, symbol/call shape, protected failure,
  return validation, and evidence status. A fake adapter result is local-only.

### 3. Native/canonical identity mismatch

- **Evidence:** `live_galaxy_component_discovery.lua` converts returned IDs,
  reads owner/sector metadata, builds a canonical owner identity, and enforces
  exact owner equality. Phase 05.1 has duplicate, foreign-owner, and invalid-ID
  contracts; no complete X4 owner closure was observed.
- **Negative fixture:** return a valid native station ID whose converted Lua ID
  maps to a different owner, return duplicate IDs, or make native and canonical
  string forms disagree. The fixture must yield health/diagnostic output and no
  complete observation.
- **Gate check:** require distinct native, Lua, 64-bit, canonical-owner, and
  sector fields plus conversion provenance.

### 4. Invented unmeasured bounds

- **Evidence:** Phase 05.1 initially used a small owner-scope assumption; an X4
  run observed Argon scope greater than 16 and emitted `enumeration_overflow`.
  The old 64-station limit is explicitly superseded. X4 Live MCP's limits are
  precedent for its own producers, not Live Galaxy measurements.
- **Negative fixture:** dossier declares a count/byte/time/allocation bound but
  omits source, measured observation, or experiment ID; or labels a transport
  bound as a native allocation bound.
- **Gate check:** reject every numeric limit lacking bound type, evidence source,
  measurement context, and failure behavior. Candidate bounds remain
  `UNKNOWN` until measured.

### 5. Partial results represented complete

- **Evidence:** Phase 05.1 plans require no marker on overflow, unsupported,
  foreign-owner, duplicate, or fill mismatch. Runtime code discards pending
  frames and suppresses markers after failure. Existing X4 evidence observed
  `facts_unsupported` without a complete fact set.
- **Negative fixture:** count says N, fill returns N, but one metadata read
  fails; or one candidate is dropped while a completion marker is emitted. The
  gate must reject the completion claim.
- **Gate check:** enforce atomic admission: exact candidate count, per-member
  validity, completeness status, generation, and digest before marker/bridge
  admission.

### 6. Permissive local harness

- **Evidence:** `extensions/live_galaxy/tests/run_contracts.ps1` and contract
  suites append `extensions\?.lua`, `extensions\?\init.lua`, and
  `extensions\live_galaxy\lua\?.lua`; tests use bare `require` after adding the
  test path. `component_discovery_package_guard.ps1` and
  `01-install-guard.ps1` exist specifically because local loading can diverge
  from packaged loading.
- **Negative fixture:** create a module reachable only through the test
  `package.path` and absent from the packaged extension root. Local fake tests
  may run, but package-faithful conformance must fail.
- **Gate check:** run the same import graph twice: strict installed-like package
  root and permissive test harness. Any production-only import resolved solely
  by the latter is a failure/unknown, not a pass.

### 7. Isolated call-shape research

- **Evidence:** X4 Live MCP supplies exact-looking FFI examples, but those calls
  are embedded in its manifest/UI/MD/lifecycle/identity/failure/volume context.
  Phase 05.1 research explicitly says call shape alone does not establish
  availability, ordering, visibility, or completeness.
- **Negative fixture:** dossier contains a native function and argument list but
  no registration path, import graph, game-thread context, identity mapping,
  failure result, completeness rule, or volume/performance envelope.
- **Gate check:** each binding entry must link to all required integration
  dimensions, or be marked `UNKNOWN`; a standalone snippet cannot satisfy R1.

## Proposed executable conformance layers

The implementation should keep execution, contract, and effect verdicts
separate. A valid unexpected answer is still an unexpected answer; it is not a
passing substitute for the expected fixture.

1. **Manifest and registration layer.** Parse `content.xml` and `ui.xml`;
   validate extension ID/version/dependency, entrypoint path, environment,
   event names, and `Register_OnLoad_Init`. Include a negative fixture for
   missing dependency, wrong case, missing entrypoint, and missing registration.
2. **Package-faithful import layer.** Build an installed-like extension tree
   and resolve every transitive `require`, including production modules and
   external support modules. Reject bare imports in production files, missing
   nested imports, and test-only path dependence. Keep the permissive local
   runner only as a separately labelled test harness.
3. **Embedded-loader contract layer.** Exercise the loader/registration shape
   without asserting native success: registration once, reload idempotency,
   event name, initializer label, and lifecycle state transitions. Retain the
   existing disposable observation as load evidence only.
4. **Pure Lua layer.** Run deterministic fixtures for count validation,
   overflow before allocation, fill mismatch, duplicate IDs, invalid metadata,
   foreign owner, capacity failure, byte/frame limits, generation reset, and
   no-marker behavior. Pin the runner from
   `tools/lua-runner.lock.json`; do not infer the embedded Lua version from it.
5. **Fake-adapter contract layer.** Inject explicit adapter outcomes
   (`unsupported`, throw, malformed count, partial fill, stale/foreign
   identity, valid complete result) and assert diagnostics, no partial
   admission, and recovery. Mark this evidence `local-contract-only`.
6. **Rust/bridge admission layer.** Validate schema, semantic/safety/current
   state, completeness, generation, digest, and idempotent recovery. Reject
   stale or incomplete frames before downstream state mutation. This phase is
   verification-foundation work; it must not expand into report/command/effect
   behavior.
7. **Candidate-harness/evidence layer.** Run bounded candidates serially or in
   isolated workspaces, continue after candidate failure, emit JSONL with stable
   candidate ID/run ID, expected and actual result, completeness, elapsed real
   and game time where available, SETA state, failure point, and digest. Write
   the private full ledger under the required mode-0600 durable location and
   retain only sanitized metadata in the repository artifact.
8. **Disposable X4 layer (future residual gate).** Use only after source/static
   and pure/fake layers leave a genuinely runtime-only question. Capture setup,
   expected readback, observed readback, health, exact game/mod/scenario
   identity, and no-save/no-mutation boundaries. It is not a replacement for a
   source-resolvable answer and is out of scope for this research artifact.

## Compatibility and provenance risks

- **Mod Support APIs is a shared trust boundary.** Both installed Live Galaxy
  and X4 Live MCP depend on `ws_2042901274`. Its loader patches require behavior
  and its on-load registry are shared process-level behavior. No direct conflict
  was observed in source/manifest evidence, but duplicate registration, load
  order, protected-UI mode, and reconnect behavior require a package-faithful
  conformance fixture.
- **KUDA AI Tweaks** is installed at version `90000` and described as tactical
  AI behavior. It is a compatibility target under project policy. Its archive
  index and readable payload show extensive `aiscripts/*` and MD files, with no
  indexed UI/Lua/FFI/pipe file. This narrows static overlap to AI/MD behavior;
  merged precedence and runtime effects still require testing.
- **More AI Economy Ships** is installed at version `107` and changes economy
  jobs/trader/miner populations. It can plausibly change world volume and
  timing, but that is an inference from the manifest description, not a
  compatibility result. Measure discovery envelopes against the exact stack.
- **Add More Sectors** (`zadd_sectors`) is installed at version `117`, adds 66
  clusters per its description, and depends on several DLCs. Its CAT index and
  readable XML portions show map libraries, region definitions, sector/cluster
  assets, and MD setup files, with no indexed target UI/Lua/FFI/pipe file. It
  can alter sector enumeration volume; the resulting runtime count/order is
  still unknown.
- **Faction Enhancer** War, Econ AI, Econ Balance, and Catchup modules are
  installed at version `571`. Live Galaxy project policy says the suite is
  incompatible with the first public alpha. This is a product compatibility
  constraint, not a claim that this local install has a measured runtime
  failure. Any future coexistence test must label the suite excluded rather
  than silently treating it as a supported target.
- **No code copying.** SirNukes' support API, Treybor's mods, Mysterial's
  modules, deadair/kuertee's KUDA work, and X4 Live MCP are external sources.
  Use their manifests, documented behavior, call shapes, and architecture as
  provenance-linked evidence only. Do not copy implementation or infer a
  license from a local archive. The project has no selected license yet and
  requires a third-party provenance audit before `1.0.0`.

## Residual unknowns and saturation rationale

The dossier is saturated for the questions that can be answered from the
available loose project/reference source, installed support source/binaries,
archive indexes, and manifests: package registration, import-path failure,
support dependency and protected-loader semantics, embedded Lua engine family,
X4 Live MCP call/queue precedent, current Live Galaxy contract boundaries,
existing local negative fixtures, and the static file-class overlap of the
installed extensions. Repeating those searches would not add independent
evidence.

It is intentionally **not** saturated for the following load-bearing questions:

- authoritative vanilla signatures and return conventions for the native
  functions used by component discovery. The installed executable exposes only
  symbol strings, and vanilla XSM schemas cannot be read without an extractor;
  this is unavailable-after-local-source-exhaustion and remains a runtime
  candidate input;
- stable ordering/snapshot guarantees between native count and fill. No support
  or mod source defines an engine snapshot contract; this is intrinsically
  runtime-only after local source/archive exhaustion;
- LuaJIT extension/feature availability beyond the installed Lua 5.1/FFI binary
  evidence;
- global lifecycle ordering across unrelated extensions' `ui.xml` inclusion and
  any game-thread/context guarantee for target native calls. The support loader's
  own registration order and duplicate-init guard are source-resolved;
- measured native allocation/time ceilings, especially with Add More Sectors and
  More AI Economy Ships installed;
- final merged archive precedence and runtime coexistence/effect of installed
  target mods. Their static file-class overlap is now source-resolved;
- native owner/sector identity closure and complete X4 discovery readback.

Where an unknown might be source-resolvable, the next step is source/archive or
official API research, not a game probe. A disposable X4 candidate is justified
only after that source path is exhausted and the remaining question is
intrinsically runtime-only. Until then, the dossier remains
`INCOMPLETE_FOR_REVIEW`.
