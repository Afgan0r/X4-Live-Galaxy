# Phase 05.2: Layered Lua and X4 Verification Foundation — Specification

**Created:** 2026-08-30
**Ambiguity score:** 0.08 (gate: ≤ 0.20)
**Requirements:** 6 locked

## Goal

Every future Live Galaxy X4 seam is admitted through source-saturated evidence,
an executable known-failure gate, production-faithful conformance, and bounded
candidate experiments before implementation or in-game use.

## Background

Phase 05.1 reached X4 with loader, native-binding, identity, completeness,
bound, and test-fidelity defects even though its local checks passed. The local
runner resolved modules more permissively than X4, several fake checks repeated
the proposed implementation's assumptions, and isolated native call shapes were
treated as integration evidence. The repository has layered tests and disposable
probe procedures, but it has no universal integration dossier contract, known
X4 failure registry, executable admission gate, production-faithful conformance
suite, or multi-candidate experiment format. Phase 05.1 is paused before further
X4 runs until this foundation exists.

## Requirements

1. **Integration dossier contract**: Every X4 seam has a phase-owned dossier that
   records primary-source and independent production-precedent evidence for all
   required integration dimensions.
   - Current: Research artifacts may record individual calls or examples without
     proving loader, binding, identity, lifecycle, failure, completeness, and
     volume behavior together.
   - Target: A versioned dossier schema and validator require loader and
     registration, extension-relative module resolution, Lua/native binding,
     exact arguments and returns, native/canonical identity, lifecycle and game
     thread ownership, cadence and reconnect, failure/partial/completeness, and
     source-supported or observed volume behavior. Each field is `EVIDENCED`,
     `CONFLICTING`, or `UNKNOWN` with precise provenance.
   - Acceptance: Complete fixtures pass; omitting any required dimension,
     primary source, production precedent, status, or provenance fails before a
     seam can be planned.

2. **Known X4 failure registry**: A project-owned registry and coverage matrix
   gate every seam against all demonstrated failure classes with no automatic
   small-change exception.
   - Current: Phase-local guards cover subsets of known failures, and there is
     no canonical registry or exhaustive applicability check.
   - Target: The registry includes loader mismatch, native-binding assumptions,
     native/canonical identity mismatch, invented unmeasured bounds, partial
     results represented as complete, permissive local harnesses, and isolated
     call-shape research. Every seam maps every entry to independent dossier
     evidence plus an executable check, or to a justified not-applicable verdict.
   - Acceptance: One negative fixture per registered class reintroduces that
     defect and makes the gate fail; a missing row, evidence link, check, or
     justification also fails. Only an explicit owner override containing scope,
     reason, and remaining risk can bypass the gate.

3. **Production-faithful conformance**: Packaged Lua and X4 integration checks use
   production module-resolution, registration, binding, and import-graph behavior.
   - Current: The standalone Lua runner can load bare modules through a permissive
     package path that does not prove the packaged extension loads in X4.
   - Target: Conformance constructs or inspects the packaged extension, validates
     the complete production import graph, and exercises loaders and native
     binding acquisition under the same extension-relative rules as production.
   - Acceptance: The real package passes; fixtures with a bare production
     `require`, a test-only path dependency, missing registration, or the wrong
     native-binding acquisition fail while an equivalent test-only module remains
     clearly classified as local evidence rather than X4 evidence.

4. **Read-only candidate experiment harness**: Residual native uncertainty can be
   expressed as multiple source-derived candidates and evaluated independently in
   one developer-only run when they can coexist safely.
   - Current: Disposable procedures test one assumed path at a time and do not
     guarantee that one candidate failure leaves later candidates runnable.
   - Target: A bounded candidate manifest and developer-only runner execute
     candidates serially and in isolation, record every stage as structured
     JSONL, and assign separate execution, contract, and effect verdicts. Loader
     or registration conflicts require separate builds.
   - Acceptance: Local deterministic fixtures prove candidate ordering,
     per-candidate error isolation, continuation after failure, bounded logs, and
     distinct verdicts; a valid but unexpected answer cannot be reported as a
     pass. No X4 run is required to complete Phase 05.2.

5. **Evidence retention and decision ledger**: Full runtime evidence remains
   private and durable while committed artifacts contain only sanitized,
   reproducible conclusions.
   - Current: Probe procedures describe evidence manually but no shared schema
     binds private logs to sanitized candidate decisions.
   - Target: The harness records exact game version, mod list, scenario,
     candidate source, expected and actual results, completeness, elapsed real
     and game time, SETA state when relevant, exact failure point, run identity,
     and digest. Full JSONL stays in a mode-0600 durable machine-local artifact
     with a mode-0600 locator; the phase ledger records only safe metadata and
     retain/remove/fallback/repeat/production dispositions.
   - Acceptance: Validation rejects missing required metadata, unstable candidate
     identity, absent digest linkage, secret/private path leakage, or a verdict
     without its evidence reference.

6. **Phase 05.1 candidate matrix**: Remaining Phase 05.1 native, lifecycle, and
   transport unknowns are converted into the first source-derived candidate set
   without executing X4 or changing the Phase 05.1 production seam.
   - Current: Phase 05.1 has paused disposable checks and competing unresolved
     assumptions spread across UAT, debug, plan, and runtime evidence.
   - Target: A Phase 05.1 candidate matrix cites the completed dossier and registry
     coverage, declares expected outcomes and failure classification, and is ready
     for one later prepared X4 run owned by Phase 05.1.
   - Acceptance: The matrix contains every remaining Phase 05.1 native unknown,
     no source-resolvable uncertainty, deterministic candidate identities, and no
     mutation or automatic game execution.

## Boundaries

**In scope:**

- Versioned integration dossier schema, examples, and completeness validation.
- Known X4 Failure Registry, exhaustive applicability matrix, admission command,
  and negative fixtures for every initial failure class.
- Production-faithful packaged conformance for current Lua, lifecycle, and
  transport integration.
- Developer-only read-only multi-candidate manifest, isolated runner contracts,
  JSONL evidence schema, and sanitized decision-ledger format.
- A prepared Phase 05.1 candidate matrix for its remaining native unknowns.

**Out of scope:**

- Executing the pending Phase 05.1 X4 run — it remains the human verification
  gate that closes Phase 05.1 after this foundation exists.
- Mutating X4 APIs, commands, or state — later mutation phases extend the same
  contract with disposable-campaign isolation and independent effect readback.
- Lua hot reload — it is not a product goal and remains unsupported unless a
  later phase proves it safe.
- General Phase 6 reports, Mail, or Logbook behavior — this phase supplies only
  developer evidence and admission infrastructure.
- Copying third-party mod code or treating unlicensed implementation as a
  production dependency — external sources are evidence and precedent only.

## Constraints

- X4 9.00, the game installation, and installed extensions are read-only
  evidence sources; save files are never inspected or modified.
- Source collection cannot issue PASS or BLOCK; an independent planning or
  verification gate owns admission.
- Source-answerable uncertainty cannot be deferred to an in-game probe.
- All work, payloads, logs, retries, candidates, and game-thread operations are
  explicitly bounded; bounds must be measured or source-supported.
- Fake adapters prove local contracts only and cannot serve as independent X4
  runtime evidence.
- The public package excludes developer-only candidate controls and detailed
  trace output.

## Acceptance Criteria

- [ ] A complete dossier fixture passes and every missing required field or
  provenance class fails.
- [ ] All seven initial Known X4 Failure Registry defects have negative fixtures
  that fail the admission gate.
- [ ] The admission gate rejects incomplete coverage matrices and accepts only
  complete evidence/check mappings or justified not-applicable rows.
- [ ] Packaged conformance rejects bare production imports, permissive test-only
  resolution, missing registration, and incorrect native-binding acquisition.
- [ ] The read-only candidate harness deterministically continues after one
  candidate fails and reports execution, contract, and effect separately.
- [ ] Structured evidence is bounded, digest-linked, secret-safe, and separated
  between private full JSONL and sanitized committed metadata.
- [ ] The Phase 05.1 candidate matrix covers every remaining native unknown and
  contains no source-resolvable question or mutating operation.
- [ ] No Phase 05.2 check claims behavior was observed in X4 without a separately
  retained runtime run and independent expected-result judgment.
