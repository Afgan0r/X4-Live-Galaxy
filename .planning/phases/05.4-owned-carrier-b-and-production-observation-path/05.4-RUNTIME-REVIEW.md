# Phase 05.4 Runtime Corrections: Code Review Report

## Summary

The late runtime corrections do not yet satisfy the accepted recovery and
publication contracts. Four blockers remain: a game-loaded boundary can publish
pre-load in-flight data, the required compatible bridge-restart path is not
actually tested, package verification admits files and metadata outside its
integrity closure, and the packager accepts limits that the production bridge
will reject. Two additional test/convention defects make the green regression
signal incomplete.

## Narrative Findings (AI reviewer)

## Critical Issues

### CR-01: Game-loaded handling does not terminate pre-load in-flight work

**Classification:** BLOCKER (P1)

**Files:**

- `extensions/live_galaxy/lua/live_galaxy_runtime.lua:45-60`
- `extensions/live_galaxy/lua/live_galaxy_scheduler.lua:27-43`

**Root cause:** `telemetry_game_loaded` only replaces `pending_boundary`. The
scheduler then calls `carrier.progress` and `carrier.poll_control` before it
tries to reserve the fresh boundary sample. There is no lifecycle operation
that fails or discards the pre-load section, pending encoded message, or active
transfer identity and no generation/transport-epoch transition at this source
boundary.

**Violated contract/rule:** CONTEXT/RESEARCH D-04 and D-06 require failed or
incomplete transfer identities to terminate and start/load/reload uncertainty
to require a fresh qualifying baseline. The Phase 05.4 plan also requires old
handles/results not to affect new generations. `XCODE-04` requires explicit
generation fences across reload-like lifecycle boundaries.

**Evidence:** On a game-loaded callback, line 48 latches only the boundary;
lines 53-59 still execute the normal scheduler. Scheduler lines 27-32 advance
and acknowledge the old producer work before line 39 begins new evidence. The
Lua contract test covers retaining a boundary while capacity is unavailable,
but it does not seed an in-flight pre-load identity and prove that it cannot
publish.

**Consequence:** Bytes captured before a load can be completed, acknowledged,
committed, and made current after the load. If the subsequent fresh capture
fails, that stale revision remains the newest durable observation, contradicting
the explicit freshness boundary.

**Minimal correction:** Add one native lifecycle transition for
`telemetry_game_loaded` that atomically terminates the old collection and
pending transfer, advances the applicable generation/transport epoch, and
retains the fresh-boundary request. Permit collection only after the new
generation is ready. Add an actual-native test that seeds pending pre-load work,
fires game-loaded, proves the old identity cannot commit, and then commits a
newly captured baseline.

### CR-02: The process-restart scenario replaces the producer instead of testing bridge-only recovery

**Classification:** BLOCKER (P1)

**File:** `tests/carrier-b-local.ps1:190-197,209-220,240-262,290-300`

**Root cause:** The first Lua/native host is allowed to exit before the bridge
is stopped. The restart branch then launches both a new host process and a new
bridge process. Its expected two producer sessions confirm that this is a full
producer replacement, not a compatible bridge crash/reconnect against the same
live producer.

**Violated contract/rule:** Accepted D-02/D-04/D-06 require bridge-independent
startup and compatible external bridge restart without a game restart. Phase
plan line 90 requires exact reconciliation and fresh collection after that
restart. `XT-04` requires the cross-language path and revision identity to
survive process restart.

**Evidence:** Lines 209-220 wait for the producer host to exit. Lines 240-244
stop the bridge and create a second host before creating the second bridge.
Lines 297-300 require two producer sessions. The scenario therefore cannot
exercise `observe_connection` replacement, transport-epoch advancement for the
same producer incarnation, stale-teardown isolation, or same-producer fresh
collection.

**Consequence:** The mandatory recovery acceptance can pass while a real bridge
crash leaves the live producer stuck, lets stale teardown clear the replacement,
or reuses an invalid incomplete identity. This is an untested production
recovery path, not merely missing incidental coverage.

**Minimal correction:** Keep one Lua/native host alive after at least one
commit, terminate and restart only the bridge against the same data directory,
wait for that producer's connection generation to advance, and assert the
producer incarnation is unchanged, the transport epoch increments, stale
teardown cannot clear the replacement, and a fresh collection commits the next
durable revision without permanent rejection or peer-inactivity termination.

### CR-03: Package verification is not closed over the shipped file set or manifest identity

**Classification:** BLOCKER (P1)

**Files:**

- `tools/package-live-galaxy.ps1:127-149`
- `tests/x4-disposable/01-install-guard.ps1:19-48`

**Root cause:** Both verifiers iterate only the entries named by
`manifest.files`; neither compares them with the actual recursive file set nor
contains each manifest-relative path under the package root. The install guard
also does not reapply `Assert-Manifest`: it never validates product/candidate,
ABI 2, control 3, envelope 2, or semantic 1/2/3/1 identity.

**Violated contract/rule:** `TOOL-03` requires an exact publication artifact and
`TOOL-05` requires checks to validate their intended inputs. Phase threat
T-05.4-SC requires package preparation to retain its legitimacy gate. The
accepted runtime contract requires exact 2/3/2 and 1/2/3/1 identities and no
game-state mutation.

**Evidence:** `Assert-Bundle` lines 144-149 and the install guard lines 41-48
verify only listed properties. The install guard lines 33-40 require four
listed files but do not reject any extra file. Its parsed manifest at line 19
is never checked against the identity predicate implemented by the packager at
lines 127-134.

**Consequence:** An unmanifested executable X4 file, for example an extra MD XML
under the extension, can be added after packaging and pass the read-only install
guard even though X4 will load it. Manifest identity fields can also be altered
without invalidating any listed-file hash. Thus a package reported as verified
can contain unreviewed mutation code or advertise a contract identity the guard
never admitted.

**Minimal correction:** Canonicalize and contain every manifest-relative path;
enumerate the package recursively; and require exact set equality between all
package files and manifest entries, excluding only `manifest.json`. Reuse one
manifest-identity validator in both packaging and install verification,
including candidate and the complete ABI/control/envelope/semantic tuple. Add
negative tests for an extra MD/Lua file, traversal entry, and altered identity.

### CR-04: The ready-package path accepts limits the production bridge rejects

**Classification:** BLOCKER (P1)

**Files:**

- `tools/package-live-galaxy.ps1:90-104,165-174,278-285`
- `crates/x4-bridge/src/production_limits.rs:45-81`

**Root cause:** The PowerShell packager checks only field count, numeric type,
and positivity. The production parser additionally rejects duplicate fields and
requires six cross-field relationships, including
`complete_message_bytes <= max_pending_bytes <= max_total_bytes`. These are two
different admission contracts for the same production configuration.

**Violated contract/rule:** `TOOL-05` requires checks to validate intended
inputs and fail honestly. The ready-package workflow promises a production
candidate, so its configuration admission must agree with the bridge that will
consume the packaged bytes.

**Evidence:** `Read-Limits` returns the raw input at line 103 after only the
shape/positive checks at lines 95-102. `Write-Bundle` packages those bytes at
lines 165 and 174, and the ready path reports `READY_PACKAGE` at lines 278-285.
By contrast, `ProductionLimits::parse` calls `relationships_valid`, whose six
additional constraints are at `production_limits.rs:73-81`; its insertion
logic also rejects duplicate keys.

**Consequence:** A user-supplied positive, correctly shaped limits file can
produce a package labeled ready that deterministically fails bridge startup.
This makes the release gate claim false and defers a configuration error until
the user-operated checkpoint.

**Minimal correction:** Make packaging invoke the same authoritative parser as
the bridge (prefer a bridge `--validate-limits` mode or a shared schema/parser)
and package only its byte-identical accepted input. Add package negatives for
every cross-field relationship and duplicate keys.

### WR-01: The default Lua regression hides a broken obsolete loading suite

**Classification:** WARNING (P2)

**Files:**

- `extensions/live_galaxy/tests/run_contracts.ps1:54-67`
- `extensions/live_galaxy/tests/module_loading_spec.lua:180-258`

**Root cause:** The `all` suite excludes `module_loading_spec.lua` from normal
execution and later runs only its `#syntax` cases. The excluded normal cases
still target the removed Carrier A/pipe runtime (`Register_OnLoad_Init` and
`runtime.emit`).

**Violated contract/rule:** `TEST-03` requires real boundary coverage and
`TOOL-05` requires the full check to execute its intended inputs. The accepted
architecture explicitly removes the Carrier A/Mod Support APIs runtime path.

**Evidence:** Runner line 62 lists four files but not the loading spec; lines
60 and 67 select only the syntax tag. Direct normal execution of that file with
the pinned Lua/Busted runner returned exit 1: 16 successes, 1 failure, and 5
errors. The failure begins at line 180 and the errors exercise obsolete
`runtime.emit` calls at lines 204-233 and 254 onward.

**Consequence:** The advertised full Lua regression is green while reviewed
test source is red and continues to encode the prohibited legacy architecture.
Future loader/runtime regressions can remain hidden behind the syntax-only tag.

**Minimal correction:** Remove or migrate the obsolete normal cases to the
Carrier B loader/scheduler/native contract, then include the resulting loading
suite in `all`. Keep syntax validation as a separate stage rather than using it
to mask the behavioral cases.

### WR-02: Three reviewed Rust test files violate the mandatory 200-line limit

**Classification:** WARNING (P2)

**Files:**

- `crates/x4-bridge/tests/carrier_b_contract.rs:201-230` (230 physical lines)
- `crates/x4-bridge/tests/production_startup/actual_pipe.rs:201-213` (213 physical lines)
- `crates/x4-carrier-native/tests/producer_contract.rs:201-281` (281 physical lines)

**Root cause:** Late scenarios were appended to already near-limit test modules
instead of being split into narrowly named scenario modules.

**Violated contract/rule:** `RUST-04` explicitly caps every Rust source file,
including tests and blank/comment lines, at 200 physical lines.

**Evidence:** Counts are from the exact reviewed Git objects at
`5cbef22f79a3f9aafb4d45324dddc2a502b82a82`, not from later evidence commits.

**Consequence:** The implementation violates a mandatory repository convention
and leaves dense cross-boundary tests harder to review and extend without
coupling unrelated scenarios.

**Minimal correction:** Move cohesive scenario groups into narrowly named test
modules while preserving the same public fixtures and assertions; keep each
resulting Rust file at or below 200 physical lines.
