## Producer ownership amendment: 2026-09-07

The separate architecture discussion checked the historical thin-adapter
decision against current architecture, Phase 01/05.1 precedents, Phase 05.4
research/plans, implemented Rust boundaries and the registered X4 family memory.
Historical evidence did not establish that the DLL had already been selected
as the complete producer. The later transport-only DLL boundary and planned Lua
SHA-256/certificate implementation were explicit current requirements.

| Option | Responsibility and consequence | Disposition |
| --- | --- | --- |
| A | Lua assembles complete protocol messages; native code transports bytes. Retains cross-language canonicalization. | Replaced |
| B | Lua supplies game observations; the DLL assembles complete producer messages. Loaded producer changes remain game-facing updates. | Owner approved |
| C | Pure Rust producer code is separated from transport and reused where useful. | Useful organization within B; no extra abstraction or crate mandated |

The owner explicitly approved B and GSD documentation changes. After the
certificate explanation below, the owner also approved D-13. These decisions
authorize the architecture amendment, not resumed phase implementation. The
accepted boundaries are captured in D-12 and D-13 of `05.4-CONTEXT.md`.

The owner asked how bridge-to-game commands coexist with the prohibition on
background Lua/X4 calls. The explanation distinguishes message delivery through
bounded native IPC/buffering from eventual game API execution inside an admitted
Lua callback. Future game commands remain outside Phase 05.4; no new command
capability was requested or admitted by that clarification.

The owner also requested a simpler explanation of `decoded_bytes`. Source
inspection found that it includes the Rust `EnvelopeRecord` layout charge and
is compared with a receiver-side calculation. Identical protocol content can
therefore disagree across producer/receiver builds with different layouts.
The owner challenged why exact memory use should be measured or transmitted
at all. The follow-up source check showed that this is only an accounting
estimate and that the receiver independently checks its own per-batch and
aggregate limits before retaining a new staged batch. Transmitting the estimate
in the terminal certificate adds no necessary capacity-admission evidence.

The lead withdrew the framing of retaining this coupling as an equally
justified architecture option. The owner approved removing the internal-memory
estimate from the protocol, preserving message/record/queue limits and requiring
more elaborate local accounting only for a concrete uncovered resource risk.
Exact per-packet RAM measurement is not a requirement. Certificate integrity
checks remain; version/compatibility details require amended research and plans.

The amendment also checked the registered `X4.native_module.packaging` and
`X4.native_module.lifecycle` entities against `x4-9.00-steam-23660954`,
`carrier-b-native-boundary-source-20260904-v1` and
`carrier-b-native-boundary-runtime-639726fa-v1`, with complete inspection
pagination. Source-resolved Lua C module loading and bounded probe observations
do not establish general hot replacement, automatic save safety or permission
for background game API calls. No new runtime experiment was performed.
