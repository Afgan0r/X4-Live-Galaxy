### Locked Decisions

## Locked decisions from the split

- Phase 05.3 remains source-agnostic and owns generic Rust contracts, validation and durable publication.
- This phase owns the minimal Live Galaxy-controlled production carrier and the X4-to-Rust observation path behind the Phase 05.3 carrier-neutral facade.
- Carrier B is a minimal Rust/C native library with a Lua-facing boundary. It is not a general plugin platform and does not own observation policy, publication policy or strategic behavior.
- Carrier B replaces `sn_mod_support_apis` in the production runtime path. Carrier A remains research and comparison evidence, not a required Live Galaxy dependency or an automatic runtime fallback.
- The owned DLL is implemented in Rust and exposes a minimal C ABI that X4's LuaJIT runtime calls through FFI. "C ABI" defines the binary calling contract; it does not require a separate C implementation layer unless later research proves one necessary.
- The intended boundary is `X4 UI Lua -> LuaJIT FFI -> exported C ABI -> Rust carrier implementation -> local IPC/Rust ingestion`. Exact exported functions and result codes remain research and discussion decisions.
- Lua owns X4 getters, cooperative scheduling and final admission of each native step. The DLL receives only bounded caller-owned buffers and returns bounded typed transport outcomes; it does not move X4 getter ownership into Rust.
- The DLL copies accepted input synchronously into memory it owns before retaining or processing it. Background Rust work may use only DLL-owned memory and must not retain LuaJIT/X4 pointers or call Lua/X4 APIs.
- The FFI boundary catches panics and failures and must never unwind into X4. Any required `unsafe` Rust is confined to the smallest reviewed ABI boundary for pointer validation and copying.
- The transport exposes no fleet, economy, diplomacy, institution or other game-state mutation command.
- Complete-message, connection, capacity, send, receive, control-poll, duplicate, permanent rejection and ambiguous outcomes remain distinct and bounded.
- Retry preserves the exact immutable batch identity and bytes. A local native write is not a volatile `received` acknowledgement or durable `committed` receipt.
- Carrier A (`sn_mod_support_apis`) is retained as research evidence and may not be presented as a safe fallback unless new executable evidence closes its bounded nonblocking and typed-result gaps.
- Automatic save pause/resume is unsupported under current evidence. A numeric cooldown must not be invented from the historical implementation.
- Heavy faction-ship conformance belongs to Phase 05.5 and the conditional station remainder to Phase 05.6.

## Decisions from the Dedicated Discussion

### Distribution and startup

- **D-01:** Deliver a coherent portable Windows package containing the mod with
  its owned DLL and the external Rust bridge. Preserve the agreed Rust C ABI
  boundary; no additional C implementation layer is selected.
- **D-02:** X4 and the bridge start independently, in either order, and connect
  automatically. The user starts X4. A compatible external bridge may restart
  without restarting X4; changes to game-facing code or incompatible game-side
  protocol revisions retain the existing restart boundary.
- **D-03:** Joint startup/shutdown automation is deferred to public installation
  design. No personal shortcut, launcher, process watcher, or automatic bridge
  process supervisor is a required Phase 05.4 deliverable.

### Failure recovery

- **D-04:** After a temporary transport failure exhausts the current send
  retries, stop the failed transfer and pause collection. Enter bounded
  availability checking rather than an immediate resend/rescan loop. After
  reconnection and compatibility confirmation, start fresh collection.
- **D-05:** Target one availability check every **five seconds of real time**.
  With continuing game callbacks, reconnection should normally be detected
  within that interval. Pause/load have no five-second guarantee. This is an
  owner-approved responsiveness target, not a measured safe production limit:
  research must establish check cost, scheduling feasibility and final values.
- **D-06:** Automatic connection recovery does not restart a crashed bridge
  process, waive version incompatibility, or prove a source boundary. Preserve
  exact immutable retry within its valid scope, discard incomplete work at
  reconnect, reconcile durable receipts and never duplicate publication.
  Start/load/reload uncertainty requires a fresh qualifying baseline; previous
  accepted revisions remain history-only across an uncertain source boundary.

### Overload and diagnostics

- **D-07:** Expose a concise console status for connection, collection, waiting
  and degradation with its reason. Retain detailed structured developer history
  under the existing logging contract. A bridge web interface is deferred in
  `SEED-001`, not admitted as an HTTP/API or frontend task here.
- **D-08:** Preserve Phase 05.3 backpressure and freshness rules: pump before
  collection, reserve capacity before producing work, pause at a bounded
  continuation and retain immutable pending bytes. Never repeat getters for a
  transport retry. Independent resource limits remain finite; stale required
  observations block dependent decisions rather than being reported as fresh.
  This is an inherited contract, not a newly selected overload algorithm.

### Disposable X4 acceptance

- **D-09:** Prove a small real observation flow from X4 through the owned DLL
  and Rust ingestion to independently verified durable publication. Include
  reconnection, load/UI reload and sustained SETA as well as ordinary time.
  Local fake success and synthetic transport traffic alone cannot close this
  real observation acceptance boundary.
- **D-10:** The minimum acceptance setup is vanilla X4 plus DLC and Live Galaxy
  with necessary dependencies. Broader coexistence testing with other supported
  mods belongs to later stages; public compatibility obligations are preserved.
  Necessary dependencies do not reintroduce Carrier A as a runtime fallback.
- **D-11:** The user performs every in-game action under a written disposable
  verification plan. Agents may prepare instructions and interpret retained
  evidence; they never start/control X4 or read/modify saves.

## Summary

Phase 05.4 should be planned as replacement of the historical Carrier A runtime, not as an incremental wrapper around it. The current UI runtime still declares and calls `sn_mod_support_apis`, while the carrier-neutral Rust facade has no production implementation. [VERIFIED: `extensions/live_galaxy/ui.xml:4-7`; `extensions/live_galaxy/lua/live_galaxy_runtime.lua:73-108`; codebase structural query `ast-index usages ObservationCarrierFacade`] The phase must therefore connect a new owned `cdylib` through that facade to the existing Phase 05.3 lifecycle and durable repository, and must remove the production dependency rather than retain an automatic fallback. [VERIFIED: `.planning/phases/05.4-owned-carrier-b-and-production-observation-path/05.4-CONTEXT.md:25-41,203-218`]

The production design should use a tiny versioned C ABI, opaque generation-checked handles, synchronous copying of caller bytes, a fixed one-message data slot, and a bounded control/result slot. Lua pumps transport before collection, retains immutable pending bytes until a receiver outcome, and performs no new getter work while waiting or retrying. [ASSUMED] The DLL owns only transport state; the external bridge owns capability negotiation, validation, reconciliation, and `ObservationLifecycle` durable publication. [VERIFIED: `.planning/phases/05.3-generic-observation-contracts-and-durable-publication/05.3-CONTEXT.md`; `crates/observation-application/src/lifecycle.rs`; `crates/observation-application/src/lifecycle_publication.rs`]

### Pattern 1: One Loader Export, Versioned Opaque Module API

Export exactly the `luaopen_<module>` initializer selected by the package wrapper. The initializer creates a narrow Lua module API whose functions exchange fixed-width values and caller-provided buffers. Keep `abi_version` and `struct_size` first in configuration/output records, represent the session handle as an opaque integer token containing a generation, and validate every token lookup. Do not expose Rust enums, Rust allocations, or raw internal pointers. [VERIFIED: x4-docs `X4.native_module.packaging`; `package.loadlib`] [ASSUMED]

Freeze the owned Phase 05.4 package contract as path `.\extensions\live_galaxy\ui_c_library_live_galaxy_carrier_64.txt` and symbol `luaopen_live_galaxy_carrier`. This follows the exact installed 1.95 extension-root `.txt` convention while giving the artifact and initializer Live Galaxy-owned identities; both values require static package tests and normal-loader runtime confirmation before acceptance. [ASSUMED]

Recommended logical module operations (names remain research proposals; the PE export allow-list contains only the chosen `luaopen_<module>` initializer): [ASSUMED]

```c
uint32_t lg_carrier_abi_version(void);
int32_t lg_carrier_open(const struct lg_open_config *config, uint64_t *out_handle);
int32_t lg_carrier_connection(uint64_t handle, struct lg_connection *out_state);
int32_t lg_carrier_try_send(uint64_t handle, const uint8_t *bytes, size_t len);
int32_t lg_carrier_poll(uint64_t handle, uint8_t *out, size_t capacity, size_t *out_len);
```

These are logical C-ABI entry contracts registered into the returned Lua module, not additional required PE exports. The result mapping must preserve the existing facade distinctions. The source-of-truth values are quoted verbatim: `ConnectionState = { Disconnected, Connected(TransportEpoch) }`; `FacadeError = { StaleEpoch, MessageTooLarge, TransportUnavailable, InvalidControlLimit }`; `CompleteMessageSendOutcome = { LocalHandoff, CapacityUnavailable, Rejected(FacadeError) }`; `ControlPollOutcome = { NoMessage, Message(ControlEnvelope), LimitReached, Rejected(FacadeError) }`. Do not equate an ABI-local copy result with `Received` or `Committed`. The source-of-truth stages are quoted verbatim: `DeliveryStage = { CollectionProgress, LocalHandoff, Received, Committed, TerminalRejection, AmbiguousPublication }`; `ReceiverDisposition = { CapacityUnavailable, Received, Committed, TimedOutOrSuperseded, StaleEpoch, PermanentlyRejected, AmbiguousCommit }`. [VERIFIED: `crates/observation-ingest/src/feedback.rs:57-76`]

### Pattern 2: Synchronous Copy, Asynchronous Progress

At `try_send`, reject null/nonzero combinations, lengths above the negotiated limit, integer-conversion overflow, stale handles, or occupied capacity before dereferencing. Copy accepted bytes into one DLL-owned allocation during the call and retain no Lua pointer. LuaJIT documentation warns that a pointer does not anchor the underlying cdata, while external-call arguments are kept alive only until the call returns. [CITED: https://luajit.org/ext_ffi_semantics.html]

Transport progress must be nonblocking from Lua's perspective. Use one owned message slot and at most one pending OS operation; `poll` advances or reads completion and returns immediately. [ASSUMED] Microsoft recommends overlapped I/O for asynchronous named-pipe operations and describes `PIPE_NOWAIT` as legacy compatibility rather than the async mechanism. [CITED: https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-type-read-and-wait-modes] Cancellation is not complete when `CancelIoEx` returns; the implementation must observe final completion before freeing or reusing its `OVERLAPPED` storage. [CITED: https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-cancelioex]

The native-boundary probe observed synchronous dispatch with maximum call depth `1`, the same observed thread id across 32 ordinary and 32 SETA samples, and very small bounded sample costs (`58` and `472` QPC ticks at 10 MHz). This supports a pulse-driven, return-immediately module API for this phase but is not a general X4 thread-affinity or reentrancy guarantee. [VERIFIED: x4-docs `X4.native_module.lifecycle`, runtime snapshot `carrier-b-native-boundary-runtime-639726fa-v1`] Prefer pulse-driven overlapped I/O over an owned worker unless implementation measurement proves that the simpler progress model cannot satisfy the bounded callback contract. In either case, copy caller bytes before return, never retain Lua state, and complete cancellation before releasing OS operation storage. [ASSUMED] [CITED: https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-cancelioex]

### Pattern 4: Explicit Recovery State Machine

Recommended states are `Disconnected`, `Connecting`, `Compatible`, `Sending`, `AwaitingReceiver`, `PausedAfterFailure`, `CheckingAvailability`, `Incompatible`, and `Degraded`. These names are proposed, not existing discrete values. [ASSUMED]

The transitions must implement this sequence: exhaust the finite retry budget for the exact immutable message; abandon that failed transfer; pause collection; check availability no more frequently than the measured real-time interval when callbacks continue; after a compatible reconnect, allocate a new transport epoch, reconcile durable receipts, discard volatile work, and begin a fresh qualifying collection. [VERIFIED: `05.4-CONTEXT.md:58-74,82-87`]

Pause, game load, and UI reload suspend any five-second detection guarantee. A reconnect check must never reset or extend the abandoned transfer's retry budget. [VERIFIED: `05.4-CONTEXT.md:60-74,148-152`]

### Pattern 5: Safe Workspace Lint Topology

The workspace currently declares `unsafe_code = "forbid"`, while the dedicated ABI must dereference a foreign pointer to make the required copy. [VERIFIED: `Cargo.toml:16-20`; `05.4-CONTEXT.md:33-35`] A child crate cannot locally relax a `forbid` inherited through workspace lints. [CITED: https://doc.rust-lang.org/reference/attributes/diagnostics.html]

Plan the lint migration explicitly: keep every existing safe crate under `#![forbid(unsafe_code)]` or an equivalent crate-level lint, let only the new native crate opt out of the workspace unsafe lint, and place every unsafe operation in a tiny documented block under `#![deny(unsafe_op_in_unsafe_fn)]`. [ASSUMED] Do not weaken the safe observation, persistence, or bridge crates to make the DLL compile. [VERIFIED: `05.4-CONTEXT.md:139-146`]

### Pattern 6: Durable Publication Is the Acceptance Boundary

The bridge-side carrier must feed the Phase 05.3 application lifecycle, not terminate at the current legacy `AcceptedProjection` server path. [VERIFIED: `crates/x4-bridge/src/server.rs`; `crates/observation-application/src/lifecycle.rs`; `crates/observation-application/src/lifecycle_publication.rs`] Acceptance succeeds only when an independent SQLite read observes the committed current revision and receipt; Lua-local success or bridge parsing is insufficient. [VERIFIED: `05.4-CONTEXT.md:89-102`]

### Anti-Patterns to Avoid

- **Retaining Lua pointers:** copy during the FFI call and keep only DLL-owned bytes. [CITED: https://luajit.org/ext_ffi_semantics.html]
- **Blocking connect/write/read on the callback:** expose bounded capacity and progress state; no wait loop in Lua or an ABI export. [VERIFIED: `05.4-CONTEXT.md:32-38,82-87`]
- **Treating local handoff as receipt:** keep local, volatile receiver, and durable outcomes separate. [VERIFIED: `crates/x4-bridge/src/facade.rs:21-34`; `crates/observation-ingest/src/feedback.rs:57-76`]
- **Replaying the failed batch after reconnect:** reconnect begins fresh collection after receipt reconciliation. [VERIFIED: `05.4-CONTEXT.md:60-74`]
- **Reusing historical numeric constants:** the current Lua values such as `MAX_PIPE_PAYLOAD_BYTES = 2048`, FIFO thresholds, and `MAX_HEAD_RETRIES = 3` are historical implementation, not approved Carrier B defaults. [VERIFIED: `extensions/live_galaxy/lua/live_galaxy_runtime.lua:1-7,111-123`; `05.4-CONTEXT.md:104-116`]
- **Keeping Carrier A as silent fallback:** remove the production dependency from `ui.xml` and `content.xml` once the owned path passes its gate. [VERIFIED: `extensions/live_galaxy/ui.xml:4-7`; `extensions/live_galaxy/content.xml:1-4`; `05.4-CONTEXT.md:25-41`]

## Common Pitfalls

### Pitfall 1: Unwinding or Aborting Across FFI

**What goes wrong:** a panic crosses `extern "C"` or aborts the X4 process. [CITED: https://doc.rust-lang.org/reference/abi.html]

**How to avoid:** make each export a minimal wrapper around `catch_unwind`, convert every failure to a stable integer result, forbid panicking helpers and destructors in the boundary, and test injected panics. `catch_unwind` is not protection from `panic=abort`, so verify the release panic profile rather than assuming containment. [CITED: https://doc.rust-lang.org/beta/std/panic/fn.catch_unwind.html]

### Pitfall 2: Use-After-Free from Lua cdata

**What goes wrong:** after Lua calls the returned native module API, native work retains a pointer whose Lua owner has been collected or whose Lua state has been recreated. Completion of a Lua-to-native call extends no caller-buffer lifetime beyond that call. [VERIFIED: x4-docs `X4.native_module.lifecycle`; source snapshot `carrier-b-native-boundary-source-20260904-v1`]

**How to avoid:** validate and copy synchronously; retain neither pointers nor Lua callbacks; make handles opaque generation-checked integers; invalidate all old handles on reload/new incarnation. [ASSUMED]

### Pitfall 3: Loading the Right Binary Through the Wrong Contract

**What goes wrong:** implementation calls `ffi.load`, publishes extra PE exports, uses the public `.dll` layout, or assumes `ffi.C` registration. Those paths bypass the verified X4 9.00 / support-API 1.95 loading chain and can make a local fake pass while the real package fails. [VERIFIED: x4-docs `X4.native_module.packaging`, version-scoped conflict `claim:fd03c4a912158f29811a9e00f709f55e2e423f0d40ae8e21cf612f5f58692c48`]

**How to avoid:** make `ui.xml` load the real wrapper; call `package.loadlib` with one tested extension-relative `.txt` path and one exact `luaopen_live_galaxy_carrier` symbol; call the returned initializer; fail closed separately for open, symbol, and initializer errors; verify the PE export allow-list and exercise normal product loading in X4. [VERIFIED: x4-docs `package.loadlib`; owned runtime probe] [ASSUMED: owned names]

### Pitfall 4: Accidental Retry-Budget Renewal

**What goes wrong:** each five-second availability check requeues the failed bytes, causing an endless resend loop and duplicate/ambiguous publication. [VERIFIED: `05.4-CONTEXT.md:60-74,148-152`]

**How to avoid:** encode “failed transfer abandoned” as a terminal per-message state; availability checks can create a new connection epoch only, never a new attempt for old bytes. [ASSUMED]

### Pitfall 5: False Five-Second Guarantee

**What goes wrong:** game pause/load or a delayed callback makes the stated recovery target impossible. The observed 50 ms MD pulse was best-effort, paused for 42.879 seconds during pause, and had a 185.249 ms maximum during the sampled SETA run. [VERIFIED: x4-docs MD pulse inspection, snapshot `x4-probe-md-pulse-a70af158-v1`]

```rust
// Pattern derived from the Rust ABI and catch_unwind documentation.
// Exact symbol names and result numbers remain planning decisions.
#[unsafe(no_mangle)]
pub extern "C" fn lg_carrier_try_send(
    handle: u64,
    bytes: *const u8,
    len: usize,
) -> i32 {
    match std::panic::catch_unwind(|| abi::try_send_copy(handle, bytes, len)) {

        Err(_) => ABI_INTERNAL_FAILURE,

}
```

### Workerless Overlapped I/O

- **Implementation default:** use no carrier-owned worker. Permit one pending overlapped data operation and one bounded control/result operation; each Lua callback performs at most one non-waiting progress poll and returns. No callback contains a wait, drain loop, retry loop, or cancellation spin. [ASSUMED] This choice is supported by the bounded owned-module sample: synchronous depth `1`, 32 ordinary calls with maximum `58` QPC ticks, and 32 SETA calls with maximum `472` ticks at 10 MHz. [VERIFIED: x4-docs `X4.native_module.lifecycle`, runtime snapshot `carrier-b-native-boundary-runtime-639726fa-v1`]
- **Executable gate:** fake-OS tests must cover immediate completion, `ERROR_IO_PENDING`, incomplete poll, completion, cancellation requested, cancellation completion, close, and stale generation with exactly one retained operation owner. The disposable ordinary/SETA run must record callback cost and gap, slot occupancy, staged/produced rate, and backlog slope; it passes only with no synchronous wait, no unbounded callback work, `Rust staged rate >= Lua produced rate`, and the independently bounded backlog invariant. [CITED: https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-cancelioex] [VERIFIED: `docs/architecture-verification.md:329-375`]
- **Measured-later disposition:** measured transport/cancellation cost remains evidence to collect, not an architectural question. If the workerless implementation fails the gate, do not silently add a worker or ship a weaker threshold: stop Plan 05 acceptance and replan explicit worker ownership, cancellation, unload, and resource bounds. [ASSUMED]

### Payload, Retry, and Timing Bounds

- **Bring-up defaults:** `max_data_message_bytes = 2_048`, `max_control_message_bytes = 512`, one occupied data slot, one bounded control/result slot, at most two total send attempts for the same immutable bytes (initial attempt plus one retry after proven non-consumption), one progress step per callback, and `availability_check_interval_ms = 5_000` while callbacks continue. The 2,048-byte data default matches the current bridge ceiling and the exact locally observed Carrier A boundary; 512 bytes is the existing strict small-message test boundary; five seconds is owner-approved. The retry count and one-step callback cap are deliberately minimal testable defaults, not measured production claims. [VERIFIED: `crates/x4-bridge/src/listener.rs:4,54-55`; `crates/observation-ingest/tests/contract_lifecycle.rs:106-126`; x4-docs Carrier A boundary inspection; `05.4-CONTEXT.md:64-68`] [ASSUMED: two attempts and one progress step]
- **Executable gate:** test every independent limit at boundary−1, boundary, and boundary+1; prove the second failed/non-consumed send exhausts the transfer, availability checks never renew it, ambiguous completion never retries, and absent/slow/restarting bridge behavior never causes getter repetition or an extra slot. [VERIFIED: locked recovery decisions; project test standards]
- **Measured outputs before package acceptance:** freeze the hard message/control ceilings, send-attempt count, callback step cap, operation timeout/cancellation budget, and any lower availability interval only after ordinary and sustained SETA measurements. Select the minimum independently safe bound across Lua production, pipe behavior, Rust staging, and durable commit—not the largest buffer one layer accepts. The five-second interval remains a target conditional on continuing callbacks; pause/load/UI reload carry no deadline. Any increase above a bring-up default requires boundary and stability evidence; a failed gate reduces the value or blocks acceptance. [VERIFIED: `docs/architecture-verification.md:329-391`; `05.4-CONTEXT.md:64-68,104-111`]

### Same-User Windows Pipe Control

- **Implementation default:** create the server pipe with `PIPE_REJECT_REMOTE_CLIENTS` and a non-null security descriptor whose DACL grants only the required directional pipe rights to the current logon SID. Do not use the Windows default named-pipe descriptor: Microsoft documents that it also grants read access to Everyone and anonymous users, and specifically recommends the logon SID to prevent access from remote users or another Terminal Services session. [CITED: https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights] [CITED: https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createnamedpipea]
- **Protocol binding:** after OS admission, require the existing capability/version/session/epoch handshake before accepting data. The DACL authenticates the Windows logon boundary; the handshake fences compatibility and lifecycle. Neither mechanism is treated as remote authentication, and no secret-bearing network protocol is added. [VERIFIED: locked context] [ASSUMED]
- **Executable gate and fallback:** tests must show current-logon access succeeds, a token outside the permitted logon SID is denied, the pipe reports remote-client rejection, a null/default descriptor is absent from production construction, and incompatible or stale handshake traffic is rejected before data admission. If the explicit DACL or remote-rejection flag cannot be established, Plan 01 fails closed; there is no unsecured/default-descriptor fallback and no Carrier A fallback. [CITED: https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights] [VERIFIED: locked Carrier A decision] [ASSUMED: test harness]

No unresolved research question remains. Runtime measurements still determine the final production constants, but their starting values, acceptance gates, failure behavior, and owner are explicit enough for checked planning. [ASSUMED]
