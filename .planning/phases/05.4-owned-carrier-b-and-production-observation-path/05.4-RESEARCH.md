## Locked decisions from the split

- Phase 05.3 remains source-agnostic and owns generic Rust contracts, validation and durable publication.
- This phase owns the minimal Live Galaxy-controlled production carrier and the X4-to-Rust observation path behind the Phase 05.3 carrier-neutral facade.
- Carrier B is an owned Rust native library with a Lua-facing boundary. Under D-12 it contains bounded producer assembly and separately owned transport responsibilities. Global collection policy, receiver admission, publication policy and strategic behavior remain in the external bridge; no general plugin platform is selected.
- Carrier B replaces `sn_mod_support_apis` in the production runtime path. Carrier A remains research and comparison evidence, not a required Live Galaxy dependency or an automatic runtime fallback.
- The owned DLL is implemented in Rust as a Lua C module loaded through the source-resolved `package.loadlib` and `luaopen_live_galaxy_carrier` initializer. The C ABI does not require a separate C product implementation. Existing FFI calls to X4 getters are a separate boundary from module loading.
- The amended boundary is `X4 UI Lua -> owned Lua C module -> Rust producer -> bounded local IPC -> external Rust ingestion`. Exact typed producer inputs and module operations require amended research and checked planning.
- Lua owns X4 getters, X4-specific resumable collection and final game-callback admission. It supplies bounded typed observations and capture evidence to the DLL. The DLL assembles complete protocol messages; Lua does not implement their canonicalization, SHA-256 or completion certificate.
- The DLL copies accepted input synchronously into memory it owns before retaining or processing it. Background Rust work may use only DLL-owned memory and must not retain LuaJIT/X4 pointers or call Lua/X4 APIs.
- The FFI boundary catches panics and failures and must never unwind into X4. Any required `unsafe` Rust is confined to the smallest reviewed ABI boundary for pointer validation and copying.
- The transport exposes no fleet, economy, diplomacy, institution or other game-state mutation command.
- Complete-message, connection, capacity, send, receive, control-poll, duplicate, permanent rejection and ambiguous outcomes remain distinct and bounded.
- Retry preserves the exact immutable batch identity and bytes. A local native write is not a volatile `received` acknowledgement or durable `committed` receipt.
- Carrier A (`sn_mod_support_apis`) is retained as research evidence and may not be presented as a safe fallback unless new executable evidence closes its bounded nonblocking and typed-result gaps.
- Automatic save pause/resume is unsupported under current evidence. A numeric cooldown must not be invented from the historical implementation.
- Heavy faction-ship conformance belongs to Phase 05.5 and the conditional station remainder to Phase 05.6.

## Decisions from the Dedicated Discussion

### Distribution and startup

- **D-01:** Deliver a coherent portable Windows package containing the mod with
  its owned DLL and the external Rust bridge. Preserve the agreed Rust C ABI
  boundary; no additional C implementation layer is selected.
- **D-02:** X4 and the bridge start independently, in either order, and connect
  automatically. The user starts X4. A compatible external bridge may restart
  without restarting X4; changes to game-facing code or incompatible game-side
  protocol revisions retain the existing restart boundary.
- **D-03:** Joint startup/shutdown automation is deferred to public installation
  design. No personal shortcut, launcher, process watcher, or automatic bridge
  process supervisor is a required Phase 05.4 deliverable.

### Failure recovery

- **D-04:** After a temporary transport failure exhausts the current send
  retries, stop the failed transfer and pause collection. Enter bounded
  availability checking rather than an immediate resend/rescan loop. After
  reconnection and compatibility confirmation, start fresh collection.
- **D-05:** Target one availability check every **five seconds of real time**.
  With continuing game callbacks, reconnection should normally be detected
  within that interval. Pause/load have no five-second guarantee. This is an
  owner-approved responsiveness target, not a measured safe production limit:
  research must establish check cost, scheduling feasibility and final values.
- **D-06:** Automatic connection recovery does not restart a crashed bridge
  process, waive version incompatibility, or prove a source boundary. Preserve
  exact immutable retry within its valid scope, discard incomplete work at
  reconnect, reconcile durable receipts and never duplicate publication.
  Start/load/reload uncertainty requires a fresh qualifying baseline; previous
  accepted revisions remain history-only across an uncertain source boundary.

### Overload and diagnostics

- **D-07:** Expose a concise console status for connection, collection, waiting
  and degradation with its reason. Retain detailed structured developer history
  under the existing logging contract. A bridge web interface is deferred in
  `SEED-001`, not admitted as an HTTP/API or frontend task here.
- **D-08:** Preserve Phase 05.3 backpressure and freshness rules: pump before
  collection, reserve capacity before producing work, pause at a bounded
  continuation and retain immutable pending bytes. Never repeat getters for a
  transport retry. Independent resource limits remain finite; stale required
  observations block dependent decisions rather than being reported as fresh.
  This is an inherited contract, not a newly selected overload algorithm.

### Disposable X4 acceptance

- **D-09:** Prove a small real observation flow from X4 through the owned DLL
  and Rust ingestion to independently verified durable publication. Include
  reconnection, load/UI reload and sustained SETA as well as ordinary time.
  Local fake success and synthetic transport traffic alone cannot close this
  real observation acceptance boundary.
- **D-10:** The minimum acceptance setup is vanilla X4 plus DLC and Live Galaxy
  with necessary dependencies. Broader coexistence testing with other supported
  mods belongs to later stages; public compatibility obligations are preserved.
  Necessary dependencies do not reintroduce Carrier A as a runtime fallback.
- **D-11:** The user performs every in-game action under a written disposable
  verification plan. Agents may prepare instructions and interpret retained
  evidence; they never start/control X4 or read/modify saves.

### Producer ownership amendment

- **D-12 (approved 2026-09-07):** Select option B: the DLL owns the observation
  producer state machine, protocol identities and envelopes, batch assembly,
  canonical serialization, digests, completion certificates and immutable
  application data retained for retry. Lua supplies X4 facts, capture metadata,
  lifecycle signals and explicit collection completion or failure. The DLL must
  not manufacture source identity or strengthen the supplied coverage evidence.
- Pure Rust protocol code may be reused by the producer and receiver. Receiver
  validation independently recomputes evidence from received content; shared
  code does not authorize trusting the producer's claimed digest or outcome.
  A new crate or general abstraction is not selected merely for symmetry.
- The external bridge continues to own global collection policy, admission,
  private staging, SQLite, receipts, publication, recovery, strategy and LLM
  work. It combines validated sender evidence with receiver-owned current
  revisions, dependencies, durable pointers, clocks and resource limits.
- Updating the loaded DLL producer is a game-facing update under the existing
  X4 restart contract. Compatible external bridge updates remain independent.
  Neither native module reload observations nor Rust implementation language
  establish safe hot replacement of the loaded product.
- The prohibition on background Lua/X4 calls concerns execution-thread
  ownership. It does not prohibit inbound messages. Future separately admitted
  game commands may arrive through bounded IPC/native buffering and be applied
  only from an admitted Lua game callback after final validation. Phase 05.4
  still exposes observations and bounded collection/control traffic only.

### Certificate and resource-accounting amendment

- **D-13 (approved 2026-09-07):** Remove the internal-memory estimate
  `decoded_bytes` from the wire/completion certificate. Do not replace it with
  another sender claim about the receiver's allocation layout. Retain
  protocol-defined record/batch counts, canonical byte measures and digests,
  independently checked by the receiver.
- Preserve enforceable local limits on message size, records, batches,
  in-flight work and aggregate queues. The receiver continues to admit each
  batch against its own limits; an end-of-transfer certificate is not a
  capacity reservation or a substitute for incremental admission.
- Exact per-packet RAM measurement is not required. The current formula
  combines canonical byte length with `record_count * size_of::<EnvelopeRecord>()`;
  it is an accounting estimate, not measured process memory. Retain or refine
  a separate local memory estimate only when necessary to cover a concrete
  resource risk that the simpler enforced limits do not cover.
- Research must specify the affected wire/certificate version and
  compatibility handling before implementation. This approval does not permit
  silently reinterpreting existing bytes, discarding durable observations or
  weakening the existing rejection, recovery and publication guarantees.

## Summary

The approved architecture is no longer a transport-only DLL. The loaded Rust DLL must own the bounded producer state machine from admitted typed facts through section envelopes, canonical bytes, digests, completion certificate and immutable retry material. Lua remains the X4-thread adapter: it invokes getters and resumable collection steps, validates X4-local shapes, supplies source/capture/coverage evidence, and calls a small typed module API. The external bridge remains an independent trust boundary and must reconstruct receiver context, recompute certificate evidence from received content, enforce its own limits and own SQLite publication/recovery. [VERIFIED: 05.4-CONTEXT.md:105-150]

D-13 is a breaking wire-shape change. The current strict completion wire requires `decoded_bytes`, the current decoder admits only `contract_version == 1`, and unknown fields are denied. The implementation must therefore introduce complete-message envelope contract **2**, remove `decoded_bytes` rather than aliasing it, and reject v1 on the new production session. Keep the semantic version vector **`schema=1`, `policy=2`, `canonicalization=3`, `digest=1`** because record schema, policy, canonical byte framing and SHA-256 do not change. The loaded module producer API changes from transport-only to producer-owned, so bump the native module ABI from **1 to 2**. [VERIFIED: crates/observation-ingest/src/wire.rs:19-24,72-103; crates/observation-domain/src/identity.rs:143-154; crates/x4-carrier-native/src/lib.rs:33-56; crates/observation-ingest/tests/completion_contract.rs:32-38]

Plan 05.4-01 is complete and preserved. Plan 05.4-02's committed carrier facade, publication/recovery seam and startup/readback work are retained, but its unfinished receive loop must construct context from sender evidence plus receiver-owned state. Plans 03-05 require amendment before execution: Plan 03 becomes Rust producer plus thin Lua adapter; Plan 04 packages and locally qualifies the real producer/consumer version pair; Plan 05 keeps the real-X4, reload and SETA gates with producer-aware evidence. [VERIFIED: git commits 9a755dc, 52e40cc, 6f00741, 0f7f3fe, de71ae3; 05.4-CONTEXT.md:207-241]

**Primary recommendation:** preserve the completed native worker and partial external bridge, add an ABI-v2 producer state machine inside the DLL using the existing pure Rust canonical/completion code after D-13 cleanup, expose only bounded typed fact/lifecycle calls to Lua, and admit only envelope-contract-v2 sessions in the bridge.

## Architecture Patterns

### System Architecture Diagram

```text
X4/MD callback
  -> Lua checks callback admission and advances one bounded getter/collector step
  -> Lua calls ABI-v2 typed producer operation with source/capture evidence
  -> ABI validates primitive shape/length, copies synchronously, returns typed result
  -> DLL producer advances bounded state:
       identity -> section start -> records -> ordered batches
       -> canonical bytes/digests -> completion certificate
       -> one immutable pending complete message
  -> completed Plan-01 worker sends through same-user bounded IPC
  -> external bridge performs compatibility gate
       -> strict envelope-v2 decode
       -> independent per-message/batch/candidate limit admission
       -> combine sender evidence with receiver-owned current/dependency state
       -> independently recompute counts/canonical bytes/digests
       -> reject OR atomic SQLite publish + receipt
  -> bounded control disposition returns through DLL buffer
  -> next admitted Lua callback polls/applies producer state transition
```

The diagram separates the X4 thread, loaded native module, OS transport and external process. A local DLL handoff is neither volatile `received` nor durable `committed`. [VERIFIED: crates/x4-carrier-native/tests/lifecycle_contract.rs:56-90; docs/ARCHITECTURE.md:968-998]

### Pattern 1: Typed Lua input, Rust-owned assembly

Use one module table with an ABI-v2 operation set that reflects state transitions, not wire encoding utilities:

| Operation | Lua supplies | DLL owns and returns |
| --- | --- | --- |
| `open` | Expected ABI, bounded configuration and source-scope evidence | Generation token, producer incarnation, transport epoch and compatible/disconnected state |
| `begin_section` | Section/source identity evidence, capture window, stated quality/availability/coverage, expected record bound | Section revision, start envelope and reserved producer capacity |
| `push_record` | Validated X4 entity identity, observation version and bounded content/facts | Stable record identity, canonical record retention, batch placement and bounded status |
| `finish_section` | Explicit collection-complete signal and final source evidence | Sealed batch(es), content/manifest digests and completion certificate without `decoded_bytes` |
| `fail_section` | Explicit source/collection failure class | Candidate discard/degradation; no completion certificate |
| `progress` | Work-unit allowance from one admitted callback | At most that bounded amount of assembly/transport progress and a typed state/result |
| `poll_control` | Token and message/work bound | One bounded receiver disposition/control result |
| `reset` / `close` | Current token and reason | Bounded teardown; stale generations remain rejected |

These names and the ABI-v2 grouping are the research recommendation, not existing exports. The current transport-only table is exactly `"abi_version", "open", "connection", "try_send", "poll", "reset", "close"`. [VERIFIED: crates/x4-carrier-native/src/lib.rs:33-43] Replace Lua-facing raw `try_send` with typed producer transitions; keep byte send internal to the DLL. `connection` may remain a read-only query or be folded into `progress`, but a planner must freeze one exact table and test it byte-for-byte before implementation.

All strings/buffers crossing the ABI are length-bounded and copied during the call. The DLL does not retain Lua objects, pointers or borrowed buffers. Producer work after return uses only owned values. [VERIFIED: 05.4-CONTEXT.md:34-36]

### Pattern 2: Source evidence versus protocol identity

Do not read D-12 as permission for the DLL to invent source truth. Lua supplies X4-derived source scope, entity IDs, capture window and quality/availability/coverage evidence. The producer owns volatile protocol identity (`producer_incarnation`, `transport_epoch`, section revision, batch identity/ordinal, record identity) and binds it to the supplied source evidence. It may downgrade invalid or incomplete evidence, but never turn partial/unknown/unsupported evidence into complete/fresh/available. [VERIFIED: 05.4-CONTEXT.md:107-115]

### Pattern 3: Split sender evidence from receiver-owned context

The current `CandidateContext` mixes `versions`, `capture_window`, `state`, `dependencies`, `expected_current`, and `stable_identity`. [VERIFIED: crates/observation-ingest/src/completion_types.rs:76-125] It should remain an internal frozen admission object, assembled by the external bridge from two sources:

```text
sender evidence (decoded from envelope v2)
  = versions + capture window + stated section state + source consistency/stability evidence

receiver snapshot (read at admission)
  = accepted/current pointer + dependency revision map + receiver clock + local resource limits

validated combination
  -> CandidateContext used by GenerationStager
```

Do not serialize the full internal `CandidateContext` and do not let production call sites inject it as trusted out-of-band data. Current `LifecycleInput` requires a caller-created `LifecycleContext`, and the bridge test helper supplies `CandidateContext` directly. [VERIFIED: crates/observation-application/src/types.rs:8-55; crates/x4-bridge/tests/carrier_b_support/mod.rs:49-79] The unfinished Plan 02 receive loop must decode sender evidence, query receiver-owned current state, validate the combination and only then call the lifecycle.

### Pattern 4: Independent recomputation despite shared Rust code

The producer may call shared canonicalization/completion helpers, but the receiver must rebuild its candidate from received batches and compare independently recomputed manifest/content/count evidence before publication. Current completion validation already compares candidate identity, counts, bytes, versions, coverage and recomputed digests. [VERIFIED: crates/observation-ingest/src/completion.rs:125-155] D-13 deletes only layout-coupled `decoded_bytes` comparisons; it does not delete digest, ordinal, count, version, dependency or coverage checks.

### Recommended Project Structure

```text
crates/x4-carrier-native/src/
  lib.rs                    # ABI-v2 module contract and single initializer
  producer.rs               # bounded producer state transitions
  producer_types.rs         # safe typed inputs/results and limits
  lua_producer.rs           # minimal Lua stack decode/copy/result boundary
  transport_worker.rs       # completed Plan-01 worker, preserved

crates/observation-ingest/src/
  batch_canonical.rs        # shared canonical bytes/digest, no layout estimate
  completion_digest.rs      # shared manifest/content material, no decoded bytes
  producer_completion.rs    # certificate binding used by native producer
  wire.rs / wire_decode.rs  # strict envelope contract v2

extensions/live_galaxy/lua/
  live_galaxy_carrier_b.lua # load module, supply typed facts, pump/poll state
```

A mechanical split inside the native crate is recommended only to satisfy the 200-line rule. Do not create a new shared crate merely for producer/receiver symmetry. [VERIFIED: 05.4-CONTEXT.md:113-116]

### Why v2 rather than silent v1 reinterpretation

## Common Pitfalls

### Treating DLL ownership as receiver authority

**Failure:** move `CandidateContext`, current pointers, dependencies or publication policy into the DLL. **Prevention:** serialize only sender evidence; external bridge resolves current durable state and performs independent admission. **Warning sign:** a producer test can publish without an independently constructed receiver context.

### Keeping v1 because canonical bytes did not change

**Failure:** remove `decoded_bytes` under v1 and silently reinterpret strict JSON. **Prevention:** envelope contract 2 plus exact handshake rejection. **Warning sign:** a fixture with `contract_version: 1` reaches `GenerationStager` or a v2 decoder tolerates extra `decoded_bytes`.

### Moving cross-language hashing but not producer state

**Failure:** Rust helper returns hashes while Lua still owns ordinals, batches, certificate and retry bytes. **Prevention:** typed state-transition API; no raw Lua `try_send`. **Warning sign:** production Lua contains SHA, big-endian framing, canonical JSON or terminal count/digest assembly.

### Strengthening source evidence

**Failure:** DLL treats explicit collection completion as proof of complete membership or changes unknown/partial to complete. **Prevention:** keep capture/source evidence explicit and monotonic only toward weaker claims. **Warning sign:** complete certificate creation does not require caller-supplied coverage/source evidence.

### Replacing incremental admission with terminal certificate checks

**Failure:** accept large batches because final counts will be checked later. **Prevention:** validate message size, record count, batch count, work and aggregate queue before each retained increment. **Warning sign:** producer certificate is consulted to reserve receiver capacity.

### Calling Lua/X4 from native background work

**Failure:** worker retains state/pointer or invokes callbacks to fetch the next fact. **Prevention:** synchronous copy at ABI; callbacks only poll/progress from the X4 thread. **Warning sign:** any native thread stores a Lua state, `ffi` pointer or X4 handle that requires a Lua API call.

### Confusing compatible bridge restart with producer update

**Failure:** promise no X4 restart after ABI/envelope/DLL changes. **Prevention:** compatible external receiver build may restart independently; loaded DLL/Lua or incompatible protocol updates remain game-facing. **Warning sign:** acceptance replaces the DLL while X4 remains running.
