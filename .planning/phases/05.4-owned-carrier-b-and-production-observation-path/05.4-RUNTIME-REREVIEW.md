## Original Finding Adjudication

### CR-01: Rejected with lifecycle and runtime evidence

**Disposition:** rejected with evidence.

The original finding assumed that a game load leaves the same Lua/native
producer alive long enough for `telemetry_game_loaded` to advance pre-load
pending bytes. That is not the accepted X4 lifecycle demonstrated by the
qualified runtime path:

- Attempt-12 B7 changed producer session from `x4-session-2773850038` to
  `x4-session-2773850039`, retained committed revision 68, discarded incomplete
  revision 69, and committed fresh revision 70 after compatibility.
- B8 replaced session `...0039` with `...0040`; the late callback from the old
  session was rejected as `peer-disconnected`, and fresh revision 101 committed.
- B9 repeated the lifecycle twice (`...0040` to `...0041` to `...0042`), fenced
  both old incarnations, and committed fresh revisions without duplication.

The native boundary makes the evidence meaningful: `lua_operations.rs` derives
both session and producer incarnation from the newly opened generation, while
`lua_transport.rs` permits teardown only for the active owner and prevents
stale teardown from clearing a replacement. The one-shot game-loaded boundary
then labels the fresh runtime's qualifying sample. Adding a second speculative
reset in `runtime.handle_tick` would duplicate an already observed lifecycle
rather than close a demonstrated gap.

**Evidence boundary:** This adjudication is valid for the accepted X4 load and
UI-reload lifecycle observed in attempt 12. It does not claim that arbitrary
future loader behavior preserves the same incarnation transition.

## Warnings

### WR-03: The PowerShell pre-parser remains narrower than the authoritative Rust parser

**Classification:** WARNING (P2)

**Files:**

- `tools/package-live-galaxy.ps1:92-109`
- `crates/x4-bridge/src/bin/validate_limits.rs:6-18`

**Root cause:** `Read-Limits` parses the JSON twice. Before invoking the Rust
validator, lines 101-103 accept only values represented by PowerShell as
`System.Int32` or `System.Int64`. `ProductionLimits::read` parses every value as
the target's `usize`, whose valid 64-bit range is larger. The PowerShell type
filter can therefore reject an input before the declared authoritative parser
sees it.

**Violated contract/rule:** `C-10` requires one coherent configuration
admission contract, and the CR-04 correction specifically makes the production
parser authoritative. `TOOL-05` requires the packaging check to validate its
intended input honestly.

**Evidence:** A byte-valid limits fixture differing only in
`max_blockers=9223372036854775808` was accepted by the release
`validate_limits.exe` with exit 0. PowerShell 7 decoded that same JSON integer
as `System.Numerics.BigInteger`, for which the line-102 predicate is false.
Consequently `Read-Limits` would raise `LIMIT_NOT_INTEGER` even though its
authoritative validator accepts the exact bytes.

**Consequence:** Packaging and production still disagree on the accepted
configuration language. A production-valid explicit limits file can be denied
by the ready-package path, and future parser evolution can silently remain
shadowed by the redundant PowerShell admission logic.

**Minimal correction:** Let the Rust validator own JSON shape, integer, field,
duplicate, positivity, and relationship admission. Keep only file existence,
byte-size, validator availability, and exit-status handling in `Read-Limits`,
then package the same raw bytes the validator accepted. Add one parity test
whose accepted input lies above `Int64::MAX`, or explicitly add the same upper
bound to `ProductionLimits` if such values are intentionally forbidden.
